# 회차 2026-11-01-b12r4 — 상한을 넘긴 저장을 목록에서 빼는 판 확인 (`TASK-304`)

HEAD `bf6b938` + 미커밋 `app/frontend/lib/api.ts` 임. 이 판의 `settleSaves` 는 상한(3000 ms)을 넘기면 그때 기다린 저장을 `pendingSaves` 에서 뺌. next dev 가 반영한 판을 쟀음. 스택은 그대로이고 재기동하지 않았음. 전용 런처 없이 서브에이전트로 돌았음(§1-1 규칙만 지킴). 쓰기는 이 폴더와 `/private/tmp/_b12r4-*` 뿐이었고 임시 파일은 지웠음.

## 절차

r3 의 `i5.mjs` 에 세 번째 열기를 더했음. 진도 POST 는 CDP `Fetch` 로 끝까지 붙잡음.

1. 홈에서 Start speaking 을 누름.
2. Manual 로 바꾸고 Next 를 누름.
3. Close 를 누름.
4. 300 ms 뒤 Start speaking 을 누름(두 번째 열기).
5. 연습이 열리면 Close 를 누름.
6. 300 ms 뒤 Start speaking 을 누름(세 번째 열기).

누름은 진짜 마우스임. 시각은 각 열기의 누름 기준임.

### 세 번째 열기가 다시 3 초를 기다린 까닭 (증거로 확인함)

붙잡힌 POST 의 시각은 첫 누름 기준으로 48 · 1077(Next) · 1591(Close) · **4938 · 5267** ms 임(hold1). hold2 도 같은 꼴임. 두 번째 열기의 상한은 앞의 3건만 목록에서 뺐음. 그 뒤 새 저장 2건이 생겨 붙잡혔음.

- 4938 ms: 두 번째로 연 칸의 마운트 직후 저장. next dev 의 Strict Mode 이중 마운트가 낸 것으로 보임(b12 관찰 O2).
- 5267 ms: 세 번째 열기 전의 Close 저장(언마운트 저장). 운영 빌드에서도 생김.

세 번째 열기는 이 새 저장들을 상한까지 기다렸음. 그래서 「저장이 계속 멈춰 있는 동안 닫고 열 때마다 3 초」가 남음. 상한을 넘긴 저장을 빼는 것만으로는 이 경우를 덮지 못함.

제안(택일):
- 한 번 상한을 넘긴 뒤에는 그 Day 의 새 저장을 기다리지 않음.
- 기다리는 대상을 「조회 직전 Close 가 낸 저장」으로 좁히고 상한을 짧게 둠.
- 저장이 상한을 넘기면 다음 저장부터 서버가 순서를 가리게 함. 예를 들어 클라이언트 순번을 보내 늦게 닿은 옛 저장을 버림.
