# AC11-5 실물 테스트 범위 요청서 — 캡틴 승인 요청

> **TASK-14.** 배경: `docs/design/2026-09-06-captain-response-to-status-report.md` 항목 4·20·§3(결정 20) —
> **AC11-5**(두 세션 연속 틀린 패턴에서 대화가 구별된다)는 자동 판정이 불가능하다는 결론과, "실제
> 테스트해야 하는 것 전체를 정리해 따로 진행 요청하라"는 지시. 이 문서가 그 요청서다.
>
> **이 문서는 실행하지 않는다.** 아래 절차는 **승인 후에만** 돈다. 지금까지 이 태스크에서
> 코드·DB·프로세스에 손댄 것은 **읽기 전용 조회 3건**뿐이다(§0).

---

## TL;DR — 캡틴이 고를 것 3개

| 옵션 | 뜻 |
|---|---|
| **승인** | 아래 §2 절차를 그대로 실행 (실물 마이크 2세션 + 실물 모델 호출 다수) |
| **거부** | AC11-5는 미충족으로 남긴다. `docs/design/2026-09-04-learning-coach-slice2-plan.md:2740`의 "슬라이스 2 완료 후에도 미충족으로 남는다"가 그대로 확정 |
| **범위 축소** | §5의 캡틴 결정 목록 중 일부만 승인(예: 세션 1개만, 또는 자동 관측만 먼저) |

**비용·시간 요지**(상세는 §4): 실물 마이크 세션 **2회**(각 3~5분 발화, `mic-1`·`mic-2`와 같은 규모) +
그 세션들이 만드는 `analyze_utterance` 실물 호출 **약 10~25건**(발화 수에 비례, 대역 없음) +
`plan_next_session` 실물 호출 **1회**(세션 1 종료 시 자동 기립). **금전 단위 추정치는 없다** — 이
리포의 다른 실물 호출 기록(§1의 선례)도 전부 **횟수**로만 비용을 표현했고, 이 문서도 그 관례를
따른다.

## §2. 하네스 시나리오 문서 (AC #1)

### 사전 조건 — 캡틴 결정 필요 (§5-3)

TASK-25(Implementation Notes, 2026-09-07)가 확인한 사실: **`session_plans.questions`(질문 3~5개)는
저장되지만 지시문 조립에 실리지 않는다** — `services/sessions.py`의 계획 조회가 `id`·`reason`·
`instruction` 세 컬럼만 고른다(TASK-25 노트가 인용한 `sessions.py:108-115`). 그 배선(질문 전달)이
**지금 TASK-25.2로 진행 중**이고, 그 파일은 이 태스크의 금지 목록에도 들어 있다
(다른 에이전트가 편집 중). 즉:

- **지금 돌리면**: 세션 2의 지시문에는 `reason`(자연어 한 줄)과 `instruction`(구조화 JSON, 목표
  형태·문장 길이 규칙 등)만 실리고 `questions`(패턴을 직접 겨냥한 질문 3~5개)는 실리지 않는다.
  대화가 패턴을 유발하는지는 **`reason`/`instruction`만으로 모델이 스스로 추론해야 한다** — 신호가
  약하다.
- **TASK-25.2 완료 후 돌리면**: 질문까지 실린다 — 대화가 패턴을 유발할 근거가 더 강하다.
- 이 문서는 **어느 쪽을 쓸지 결정하지 않는다** — §5-3에서 캡틴에게 묻는다.

### 절차 (승인 후 실행)

```
0. 착수 전 확인 (mic-1 §1 그대로 재사용)
   ① brew services list | grep postgresql@17            → started
   ② .venv/bin/python tests/harness/spike_nova_protocol.py --wav p1a.wav → PASS
   ③ baseline 스냅샷: error_patterns(전 패턴) · learning_sessions 수 · session_plans 수
      (§0 표를 재조회해 드리프트가 없는지 먼저 본다 — 다른 회차가 끼어들지 않았는지)

1. 세션 1 기동 — VOICE_ADAPTER=nova, WORKER_ENABLED=true(기본값 그대로, 끄지 않는다)
   백엔드: cd app/backend && VOICE_ADAPTER=nova .venv/bin/uvicorn app.api.main:app --port 8002
   (플래그는 환경변수로만 — .env를 고치지 않는다, browser_leg.md §2 규약과 동일)

2. 세션 1 — 캡틴이 마이크로 대화하며 목표 패턴을 **의도적으로 3~5회 반복**해 틀린다.
   목표 패턴 후보(§0 표 기준, 캡틴이 §5-4에서 확정):
     - 추천: article_missing_before_noun (이미 최다빈도 7·복습기한 지남 — 반복해도
       "새 패턴 발명"이 아니라 "기존 최다빈도를 굳힌다"이므로 계획의 초점 선택이 모호해질
       위험이 가장 낮다)
     - 비추천: pronunciation_* 계열 — next_review_at이 구조적으로 없어(TASK-9 미해결)
       복습 대상 집합에 못 들어온다. 아무리 반복해도 계획의 focus_pattern_ids에 실리지
       않는다(캡틴 회신 §2 항목4의 R11-9/AC11-6 분석과 같은 이유) → 이 목표로 고르면
       AC11-5 자체가 구조적으로 FAIL한다.
   세션을 정상 종료(학습 종료 버튼).

3. 자동 확인 A — 세션 1 종료 즉시, DB 읽기 전용:
   select frequency, next_review_at from error_patterns where pattern_key='<목표>';
   → 반복 전보다 frequency가 늘었는지 (mic-1·mic-2와 같은 형식의 증가분 표로 기록)

4. 자동 확인 B — plan_next_session job이 세션 종료와 같은 트랜잭션에서 자동 기립하는지
   (docs/design/2026-08-25-learning-coach-agent-design.md:72) 확인하고, WORKER_ENABLED=true이므로
   poll_interval(1초, phase1-implementation-plan.md:252) 안에 자동으로 done 되는지 본다:
   select status, attempts from analysis_jobs where job_type='plan_next_session'
    order by created_at desc limit 1;
   → done이 아니면 재시도 상한(§5-6)까지 대기, 초과 시 ERROR로 보고하고 멈춘다(새 재계산 SQL을
   손으로 만들지 않는다 — browser_leg.md §8의 실측 사고와 같은 함정).

5. 자동 확인 C — 계획이 목표 패턴을 초점으로 잡았는지, 읽는 경로가 실제로 작동하는지:
   select p.pattern_key from session_plans sp, unnest(sp.focus_pattern_ids) fid
    join error_patterns p on p.id = fid
    where sp.session_id = '<세션1 id>';
   curl http://localhost:8002/api/sessions/next-plan   (live-plan-1.md §3과 같은 관통 확인)
   → 목표 패턴이 focus 목록에 있으면 PASS, 없으면 이 시점에서 멈추고 캡틴에게 보고
     (2회차를 돌려도 의미가 없다 — 지시문 자체가 목표를 안 담았으므로)

6. 세션 2 시작 — 같은 백엔드(재기동하지 않는다). 세션 시작 화면에서 추천 이유 한 줄이
   목표 패턴을 가리키는 문구인지 사람이 먼저 읽는다(A1-0과 같은 자리, page.tsx:271).
   대화를 시작해 **5~10턴** 진행한다.

7. 사람 판정 (§3) — 대화가 실제로 목표 패턴을 겨냥한 질문/힌트를 하는지 캡틴이 판단.

8. teardown — browser_leg.md §8과 같은 원칙(baseline 대조 후 세션 삭제, error_patterns는
   복원, 이번엔 §0 baseline이 이미 있으므로 그것을 그대로 쓴다). 보존 대상: 이번에 만든
   session_plans 1행 + 두 세션(재현 근거).
```

⚠️ **이 절차는 "판정 회차 문서"의 초안이다.** 실행 중 실측이 이 절차의 세부(대기 시간, 재시도 횟수
등)를 정정할 수 있다 — `mic-1`이 자기 문서를 실행 중 두 번 정정한 것과 같은 방식(browser_leg.md
전체가 그 패턴이다). 승인은 **이 틀**에 대한 것이고 세부 재정정까지 막지 않는다.

## §3. 자동 관측 vs 사람 판정 (AC #2)

| # | 관측 대상 | 자동/사람 | 방법 |
|---|---|:--:|---|
| 1 | 목표 패턴 `frequency` 증가 | **자동** | psql (§2-3) |
| 2 | `plan_next_session` job이 `done`으로 수렴 | **자동** | psql (§2-4) |
| 3 | 계획의 `focus_pattern_ids`에 목표 패턴이 들어갔는가 | **자동** | psql join (§2-5) |
| 4 | `GET /api/sessions/next-plan`이 그 계획을 실제로 반환하는가 | **자동** | curl (live-plan-1.md §3과 동일) |
| 5 | 시작 화면 추천 이유 한 줄이 눈에 보이는가 | **자동 가능** | `frontend-verifier` 에이전트로 A1-0 재사용 가능(이 태스크 범위 밖 — 승인 시 별도 호출) |
| 6 | 지시문(`reason`+`instruction`)의 **자연어 설명이 목표 패턴을 정확히 지목하는가** | **사람** | 문장 의미 판단(`live-plan-1.md` §2 사례처럼 패턴을 문장으로 풀어 쓰므로 문자열 매칭이 아니라 독해가 필요) |
| 7 | 세션 1의 의도적 반복이 대화에 자연스럽게 섞였는가(연기 품질) | **사람** | 말하는 사람의 자기 판단 — 자동화 대상이 아니다 |
| 8 | **세션 2에서 튜터가 그 패턴을 유발하는 질문을 실제로 하는가** | **사람** | 캡틴 회신 §2 항목4가 이미 이렇게 결정했다("자동 판정 불가 … 사람 판정") — 이 문서가 재론하지 않는다 |
| 9 | 세션 2 대화가 세션 1과 "구별되는가"(AC11-5의 문면) | **사람** | 8과 같은 판정의 다른 표현 — 비교 기준이 사람의 인상이다 |

**요지**: DB·API 수준(1~4)은 전부 자동이다. **AC11-5의 핵심(8·9)은 구조적으로 사람 판정이고,
그것이 캡틴이 이미 내린 결론("자동으로는 판정할 수 없다")과 일치한다.** 이 문서가 새로 여는 것은
없다 — 다만 6·7처럼 "자동처럼 보이지만 실은 독해가 필요한" 항목을 명시적으로 갈라냈다.

## §4. 시간·비용·준비물 (AC #3)

| 항목 | 예상 횟수 | 근거 |
|---|--:|---|
| 실물 마이크 세션(Nova 음성 왕복) | **2회** | mic-1·mic-2와 같은 종류 — 이미 2회 선례가 있다 |

⚠️ **task-22가 적은 "스텁 세션 1회 = 실물 호출 4건"은 이 표의 하한 참고치다** — 그 4건은 스텁이
발화를 **3턴으로 고정**했을 때의 수치다. 실물 마이크는 발화 수가 사람이 말하는 만큼 늘어나므로
**세션당 4건보다 많다.** 이 문서가 §4 표에서 "10~25건"으로 넓게 잡은 이유가 그것이다.

### 준비물

- **캡틴의 실물 존재와 마이크** — 이 시나리오는 대역(스텁)이 낼 수 없는 실제 음성 왕복을 요구하므로
  **에이전트가 대신 진행할 수 없다.** `mic-1`·`mic-2`와 동일한 제약.
- 조용한 환경(ASR 오인식을 줄인다 — mic-1.md §2.4가 문장 쪼개짐 문제를 실측했다).
- **목표 패턴을 겨냥한 짧은 예문 3~5개**를 미리 적어 둔다(연기 일관성 확보). 예: 목표가
  `article_missing_before_noun`이면 "I bought car yesterday." / "She wants job in Seoul." 같은
  문장 — mic-1.md §1이 "발음 개입을 걸려면"에서 같은 방식(픽스처형 문장 미리 준비)을 이미 썼다.
- 백엔드가 `nova` 어댑터 + `WORKER_ENABLED=true`로 뜬 상태(§2-1). **이번 태스크의 범위 밖 —
  승인 후 실행 세션이 띈다.**
- `.harness/browser_run_id.txt`류의 회차 파일은 이 시나리오엔 없다(브라우저 레그가 아니라 마이크
  레그다) — `mic-1`·`mic-2`처럼 회차 문서 자체가 기록이다.
