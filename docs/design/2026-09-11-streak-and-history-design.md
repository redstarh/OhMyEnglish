# 연속 학습일과 학습 히스토리 설계 — TASK-3

> 이 태스크의 인수기준 넷은 **전부 설계**임 — 화면 구현은 별 태스크가 가짐(§7).

## 1. 연속 학습일의 정의 — 못 박는다 (AC#1)

**1일로 세는 단위는 `TASK-2` 의 판정을 그대로 쓴다**: 그날(학습자 타임존) **시나리오가 붙은 세션이
`status='completed'` 로 끝난 것이 1건 이상**이면 그날은 「학습한 날」이다.

⛔ **정의를 새로 발명하지 않는다.** 두 곳에서 「학습한 날」이 갈리면 화면의 연속일과 완료 문구가
서로 어긋난다. 그래서 이 설계는 `services/daily_summary.load_daily_completion` 의 술어를
**같은 SQL 조건**으로 쓴다(PRD §14 R14-2 · 설계서 `2026-09-11-daily-completion-design.md` §3).

| 항목 | 정의 |
|---|---|
| 하루의 경계 | `users.timezone` 의 달력 날짜. 앵커는 `ended_at`(마친 시각) |
| 학습한 날 | 그 날짜에 완료 세션 ≥ 1 |
| 연속 | 날짜가 **하루도 비지 않고** 이어진 구간 |
| 현재 연속일 | 마지막 학습한 날이 **오늘이거나 어제**면 그 구간의 길이. 그보다 오래면 **0** |
| 최장 연속일 | 전 기록에서 가장 긴 구간의 길이 |

⛔ **「오늘 아직 안 했다」를 끊김으로 세지 않는다.** 오늘이 끝나지 않았으므로 그것을 0으로 표시하면
**사실이 아니고**, 아침에 「연속 0일」을 본 학습자가 그날을 포기한다. 그래서 현재 연속일의 기준을
「오늘 또는 어제」로 둔다. ⚠️ 그 대가: 어제까지의 연속을 오늘 하루 종일 보여주므로 자정 직후에는
「연속 N일」이 아직 유지 중인 값이다 — 화면 문구가 그것을 「어제까지」로 읽히게 쓰면 안 된다(§2).

⚠️ **하루에 여러 개를 마쳐도 1일이다** — PRD §14 R14-5 와 같은 규약이다. 연속일은 **날짜 수**다.

## 2. 히스토리 화면이 보여주는 것 (AC#2)

| 요소 | 값의 출처 | 왜 필요한가 |
|---|---|---|
| 현재 연속일 · 최장 연속일 | 이 설계의 계산(§3) | 캡틴 노트 항목 6 이 요구한 것 |
| 날짜별 학습 여부 | `learning_sessions`(§1 술어) | 연속이 어디서 끊겼는지 보이지 않으면 연속일 수가 근거 없는 숫자가 된다 |
| 그날의 오류 요약 | `daily_error_summary`(PRD §13) | 이미 저장되는 값이다. 히스토리에서 그날을 되짚는 유일한 재료다 |
| 그날 마친 시나리오 수 | `learning_sessions` 집계 | `TASK-2` 가 이미 세는 값이다 |

⛔ **점수·등급·달성률을 넣지 않는다** — PRD §5 비범위와 이 리포의 톤 계약(*"채점하지 않습니다"*).
연속일은 사용자가 요구한 값이라 예외이고, 그것을 **다른 점수의 근거로 쓰지 않는다.**

⛔ **어느 시나리오를 마쳤는지의 목록은 `TASK-102` 가 소유한다** — 그 태스크가 「완료 현황」을
요구사항으로 갖는다. 여기서는 **개수**까지만 본다(두 태스크가 같은 화면을 다투지 않게).

## 3. 저장 구조와 계산 위치 — **재계산**을 고른다 (AC#3)

**결론: 누적 컬럼을 두지 않고 조회 시 계산한다.** 근거 셋이고 전부 확인한 것이다.

1. **입력이 불변이다.** 종료 UPDATE 가 `where … and status = 'active'` 로 막혀 있어 끝난 세션의
   `status`·`ended_at` 을 다시 쓸 수 없고 `scenario_id` 를 고치는 코드도 없다(`TASK-2` 설계서 §2).
   즉 같은 질문에 같은 답이 영구히 나온다 — `TASK-1` 이 스냅샷 표를 만든 근거가 여기서는 없다.
2. **누적 저장은 「갱신을 빠뜨리면 조용히 틀리는」 자리를 만든다.** 연속일 컬럼을 두면 세션 종료 ·
   리퍼 · 재분석 세 경로가 그 값을 함께 관리해야 하고, 이 리포는 그 형태로 이미 실패했다
   (`error_patterns.frequency` 를 두 writer 가 다른 규약으로 덮은 자리 — 함정 `H-AX`).
3. **비용이 없다.** 단일 사용자이고 하루 1행 규모다 — 366일을 스캔해도 수십 행이다.

**계산 위치**: `services/daily_summary.py`. 「오늘」의 규약(타임존 조회 · naive 거부)이 이미 그
모듈에 있고, 연속일은 그 판정을 날짜 축으로 늘린 것이다. ⛔ 다른 모듈에 두면 「학습한 날」의 정의가
둘로 갈라진다.

**계산 방법**(gaps and islands — 표준 관용구):

```sql
with days as (
  select distinct (ended_at at time zone $2)::date as day
    from learning_sessions
   where user_id = $1 and scenario_id is not null
     and status = 'completed' and ended_at is not null
),
grouped as (
  select day, day - (row_number() over (order by day))::int as island from days
)
select min(day) as from_day, max(day) as to_day, count(*) as length
  from grouped group by island order by from_day
```

연속 구간을 그대로 돌려주므로 **현재 연속일과 최장 연속일을 같은 조회로** 얻는다. 현재 연속일은
마지막 구간의 `to_day` 가 오늘이거나 어제일 때 그 `length` 이고, 아니면 0이다(§1).

## 4. 날짜 경계 (AC#4)

`users.timezone` 으로 구한다. `current_date` 를 쓰지 않는다 — 서버 세션 타임존의 날짜라 한국 시각
자정부터 오전 9시까지 하루 이른 값을 낸다(전역 시각 규약의 실측 함정 `H-S`).
「오늘」과 「어제」도 그 타임존에서 구한다 — 그 둘이 §1 의 현재 연속일 판정에 직접 들어간다.

## 5. 실측 예시 — 개발 DB, 2026-09-11 직접 조회

완료 세션이 있는 날짜와 그 구간:

| 날짜(KST) | 구간 |
|---|---|
| 2026-08-25 | 단독(1일) |
| 2026-09-01 | 단독(1일) |
| 2026-09-03 | 단독(1일) |
| 2026-09-06 | 단독(1일) |
| 2026-09-09 ~ 2026-09-10 | **2일 연속** |

⇒ **최장 연속일 = 2**. 2026-09-11 기준 **현재 연속일 = 2**(마지막 학습일이 어제이므로 아직 살아
있다). ⚠️ 오늘 하루가 끝날 때까지 완료가 없으면 내일 그 값은 0이 된다.

## 6. 남는 미결

- ⛔ **012 이전 날짜에는 `daily_error_summary` 행이 없다.** 그 표는 2026-09-11 에 생겼고 이후 분석만
  행을 만든다. 그래서 히스토리에서 과거 날짜는 **「학습은 했는데 오류 요약이 없다」** 로 보인다 —
  PRD §13 R13-7 이 「행 부재 = 그날 학습 없음」으로 읽게 한 것과 **어긋난다.**
  선택지 둘: ⑴ 과거 날짜를 한 번 백필하는 스크립트를 만든다(발생 행이 남아 있으므로 계산 가능하다)
  ⑵ 히스토리 화면이 「012 이전」을 별 상태로 그린다. **어느 쪽도 이 태스크가 정하지 않는다** —
  구현 태스크가 데이터를 보고 고른다.
- **화면의 자리**(별 화면인가 결과 화면의 절인가)는 구현 태스크가 정한다. 지금 히스토리 화면 자체가
  없으므로 새 경로(`/history`)가 유력하다.
- **연속일 문구의 어법**: 「연속 N일」이 자정 직후에 「어제까지」의 값이라는 것을 학습자가 오해하지
  않게 쓸 것(§1 의 대가).

## 7. 구현 범위는 별 태스크가 갖는다

이 태스크의 인수기준 넷은 정의·요구사항·저장 구조·타임존이고 **전부 이 문서와 PRD §15 로 닫힌다.**
계산 함수·엔드포인트·화면은 `TASK-107` 이 갖는다 — 그 태스크가 §6 의 미결 둘을 함께 닫는다.
