# 일일 학습 완료 판정 설계 — TASK-2

> 절차의 정본은 `docs/ops/data-first-design-convention.md` 임. 이 문서는 그 6단계의 산출물을 담음.
> 요구사항 정본은 `docs/PRD.md` §14 임. 태스크 상태는 Backlog.md `TASK-2` 가 소유함.
>
> 작성 2026-09-11 · 브랜치 `design/first-vertical-slice`.

## 1. 요구사항 — 사용자가 확정한 정의

사용자 확정 2026-09-11(원장 `TASK-2` 의 설명이 그 문장을 그대로 담음):

> 임의의 학습 시나리오는 사전에 생성하고, 이를 기반으로 사용자가 학습을 종료할지 이어 갈지를
> 결정함. 하나의 학습 시나리오를 마치면 이를 그날 학습을 완료한 것으로 봄.

⚠️ **원장의 제목이 낡았음** — 「일일 권장량 = 30분 내 학습 가능량」은 이전 정의임. 지금 정의는
시간이 아니라 **시나리오 1개 완주**임. 제목은 남겨 두고(다른 문서가 ID 로 가리킴) 이 문서와
PRD §14 가 정본임.

**경계 하나**: 시나리오를 **사전에 생성**하는 일은 `TASK-102` 가 소유함(사용자가 등록함 · 분야별
30개 이상 · 대화형 생성 · 완료 현황 화면). 이 태스크는 **「마쳤는가」의 판정과 그 표시**만 맡음.

## 2. 1~2단계 — 기존 스키마 확인과 판정: **아무것도 만들지 않음**

개발 DB 를 직접 조회했음(2026-09-11).

| 확인 | 값 |
|---|---|
| `learning_sessions` | `scenario_id uuid`(nullable FK) · `status text` · `started_at`·`ended_at timestamptz` 를 이미 가짐 |
| `status` 값역 | `('active','completed','failed')` — 001 의 CHECK. 넓힐 필요가 없음 |
| 실제 값 | `completed` **15행**(전부 `scenario_id` 있음) · `failed` 2행 |
| 날짜별 완료 | `ended_at` 을 `Asia/Seoul` 로 변환해 세면 2026-09-10 **4건** · 09-09 1건 · 09-06 4건 — 즉 판정에 필요한 값이 **이미 다 있음** |
| `learning_scenarios` | `id·category·level·title·prompt_template·created_at`(3행) |

판정은 **CREATE 도 ALTER 도 아님 — 재사용**임. 규약 §2 의 *"컬럼이 있는데 아무도 쓰지 않는다 →
재사용한다"* 에 해당함.

⛔ **`TASK-1` 과 달리 스냅샷 표를 두지 않음.** 그 태스크가 표를 만든 이유는 조회 시 계산의 결과가
시간이 지나면 **달라지기** 때문이었음(`target_form` 갱신 · 재분석의 발생 행 교체). 여기서는 그런
자리가 **구조적으로** 없음 — 코드를 직접 읽어 확인한 것 셋:

- `_END_SESSION_SQL` 이 `where … and status = 'active'` 로 막혀 있어 **한 번 끝난 세션의
  `status`·`ended_at` 을 다시 쓸 수 없음**(캡틴 결정 2026-09-03 — `end_session` 이 리퍼의 판정을
  덮지 못하게 한 가드임).
- 리퍼(`_REAP_ORPHAN_SESSIONS_SQL`)도 같은 조건이라 `active` 만 건드림.
- `learning_sessions` 를 고치는 UPDATE 는 네 곳뿐이고 나머지 둘은 `shadowing_item_id` ·
  `drill_turns_expected` 임 — **`scenario_id` 를 고치는 코드는 없음.**

즉 같은 질문에 같은 답이 영구히 나옴.

## 3. 3단계 — 판정의 정의와 예시

**「시나리오를 마쳤다」 = 그 세션이 시나리오를 갖고 `status='completed'` 로 끝났다.**

```sql
select count(*) as completed_scenarios
  from learning_sessions
 where user_id = $1
   and scenario_id is not null
   and status = 'completed'
   and (ended_at at time zone $2)::date = $3   -- $2 = users.timezone · $3 = 그 날짜
```

**「그날 학습을 완료했다」 = 위 개수가 1 이상이다**(AC#2 의 *"하나라도"*).

예시(개발 DB 실제 값):

| 날짜(KST) | 완료 시나리오 | 그날 완료 |
|---|--:|---|
| 2026-09-10 | 4 | 예 |
| 2026-09-09 | 1 | 예 |
| 2026-09-11 | 0 | 아니오 |

### 3.1 ⛔ 드릴 미달을 완료 판정에 넣지 않음 — 근거는 결정 10

기각한 대안: *「정상 종료 + 드릴 교대가 기대치 이상」을 완료로 본다.*
기각 이유는 **캡틴 결정 10** 임 — 드릴 미달의 **주어가 학습자가 아니라 대화 모델**이라고 그 결정이
정했고, 그래서 결과 화면은 두 수를 렌더하지 않고 사실 문장 하나만 그림
(`services/results.py` 의 `DrillTurns` 와 `page.tsx` 의 `DRILL_SHORTFALL_NOTICE` 가 그 계약을 가짐).
미달을 완료 판정에 넣으면 **학습자가 손쓸 수 없는 수 때문에 「오늘 학습을 못 마친 것」이 됨.**

⚠️ 그 대가를 적어 둠: 30초 만에 끝낸 세션도 완료로 셈. 지금은 그것을 받아들임 — 최소 길이 요건은
요구사항에 없고, 발명하면 그것이 새 임계값이 됨(PRD R11-8 의 경계와 같은 성질).

### 3.2 앵커는 `ended_at` 임

`started_at` 이 아니라 **마친 시각**으로 날짜를 그음. 자정을 넘겨 끝난 세션은 **끝난 날**의 완료로
셈 — 「마쳤다」는 사실의 시각이 그것임. 날짜 경계는 `users.timezone` 이고 `current_date` 를 쓰지
않음(전역 시각 규약 · `TASK-1` 과 같은 규약).

## 4. 4단계 — 읽는 쪽

| 항목 | 답 |
|---|---|
| 무엇을 저장하나 | **새로 저장하는 것이 없음** — 종료 시 이미 기록되는 `scenario_id`·`status`·`ended_at` 을 읽음 |
| 어느 표·컬럼에 | `learning_sessions` (기존) |
| 누가 읽나 | `services/daily_summary.load_daily_completion` → `api/daily.py` 의 `GET /api/daily-summary` → 결과 화면(`app/results/[sessionId]/page.tsx`) |
| 읽은 값으로 무엇이 달라지나 | 결과 화면이 「오늘 학습을 마쳤어요」를 보임 — 사용자가 **이어 갈지 종료할지** 그 자리에서 판단함(요구사항의 문장) |
| 읽는 쪽이 아직 없다면 어느 태스크가 소유하나 | 해당 없음 — 같은 커밋에 들어감 |

**왜 「오늘」 엔드포인트를 새로 만들지 않는가**: `GET /api/daily-summary` 가 이미 **사용자 타임존의
오늘**을 범위로 갖고 그 날짜를 응답에 실음. 완료 여부를 별 엔드포인트로 빼면 화면이 같은 날짜를
두 번 조회하고 **두 판독이 자정을 걸쳐 갈릴 수 있음.** 그래서 그 응답에 키 둘을 더함:
`completed_today`(bool) · `completed_scenarios`(int). 둘 다 **항상 실음**(`awaiting_analysis` 와 같은
규약 — 화면이 키 존재를 갈라 읽지 않게 함).

⚠️ 「오늘」 모듈은 `services/daily_summary.py` 하나로 둠. 타임존 조회·naive datetime 거부 규약이
그 모듈에 이미 있고, 다른 모듈에 다시 쓰면 **「오늘」의 정의가 둘로 갈라짐**.

## 5. 5단계 — 정합성 판정

| 대조 | 판정 |
|---|---|
| 요구사항 ↔ 표 | 만족함. 「시나리오 1개 완주」를 `scenario_id`+`status` 가 담음 |
| 표 ↔ 코드 | 읽는 코드가 §4 의 세 자리이고 같은 커밋에 들어감. 새 컬럼이 없으므로 「저장만 되고 안 읽히는 값」이 생기지 않음 |
| 설계 ↔ 실제 DB | 이 문서가 인용한 컬럼·값역·행 수는 전부 직접 조회로 확인한 값임 |
| 결정 ↔ 구현 | 결정 10(드릴 미달의 주어)이 §3.1 의 기각 근거로 착지함 |

## 6. 남는 미결

- **최소 길이 요건**을 두지 않았음(§3.1 의 대가). 필요해지면 그것은 새 요구사항임.
- **홈 화면 표시**는 이 태스크의 범위 밖임 — 요구사항의 「이어 갈지 결정」은 결과 화면에서
  성립하고, 시작 화면에도 보일지는 `TASK-3`(히스토리) · `TASK-102`(완료 현황)와 함께 볼 문제임.
- **완료 현황(어느 시나리오를 마쳤는가)** 은 `TASK-102` 가 소유함. 이 태스크는 **개수만** 셈.
