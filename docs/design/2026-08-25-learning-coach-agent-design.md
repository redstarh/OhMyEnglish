## 1. 범위

**한 문장**: 세션이 시작될 때 "오늘 무엇을 어떻게 연습할지"를 학습자의 실제 오류 이력에서 정한다.

현재는 고정 시나리오 1개가 모든 세션에 쓰인다. 이 설계는 그 자리를 **학습 코치 Agent**로 대체한다. Agent는 두 가지를 산출한다.

1. **세션 계획** — 오늘 다룰 패턴, 질문, 난이도, 추천 이유
2. **세션 지시문** — 실시간 대화 상대(Nova)가 이 학습자에게 어떻게 응대할지

이를 성립시키기 위해 **복습 스케줄(1·3·7일)의 갱신 주체도 이 설계가 확정한다**(§4.1) — 현재 `next_review_at`에 값을 넣는 코드가 없어 "오늘 복습할 목록"이 항상 비기 때문이다. `review_tasks`를 처음 사용하는 설계이기도 하다.

### 범위에 넣지 않는 것

주간·월간 리포트, 쉐도잉 과제 생성, YouTube 수집, 업무 역할극 시나리오 뱅크 확장, 다중 사용자. 다중 사용자 전환 과제는 `2026-08-25-first-slice-acceptance-criteria.md` §다중 사용자 전환에 있다(캡틴 결정 2026-08-25).

### Nova 블로커와의 관계

**이 Agent는 SigV4 블로커와 무관하게 만들 수 있다.** Claude만 호출하고, 종단 검증은 Phase 1이 만든 스텁 어댑터로 한다. 단 §5.2의 지시문 전달은 어댑터 포트를 확장하므로, 실제 Nova 반영은 Phase 2 연동 시점에 확인된다.

## 3. 구조와 데이터 흐름

### 3.1 언제 도는가 — 세션이 끝날 때 다음 계획을 미리 만든다

세션 시작 시점에 Claude를 동기 호출하면 시작이 수 초 지연된다. `PRD.md:109`("Agent 응답은 짧고 즉시성 있게")와 어긋난다. 따라서 **계획은 앞선 세션이 끝날 때 비동기로 만들어 저장하고, 세션 시작은 준비된 계획을 읽기만 한다.**

```text
세션 종료 (ended_at + status 기록)
  └─ 같은 트랜잭션에서 analysis_jobs 에 job 등록 (job_type='plan_next_session')
       └─ 워커가 claim → Claude 1회 호출 → session_plans + learner_notes 저장 (한 트랜잭션)

다음 세션 시작
  └─ 준비된 session_plans 행을 읽어 즉시 시작
       └─ 없으면 learning_scenarios 폴백 (§3.3)
```

**등록의 원자성은 Phase 1 §5.3과 같은 규약이다** — 세션 종료 기록과 job 등록을 한 트랜잭션에 둔다. 분리하면 그 사이 크래시에서 다음 계획이 영구히 만들어지지 않는다.

`job_type` CHECK에 `plan_next_session`을 추가한다. `session_id`를 대상 컬럼으로 쓰므로 기존 테이블 CHECK(`summarize_session`과 같은 형태)와 partial unique를 그대로 따른다.

### 3.2 무엇이 무엇을 정하는가 — 승인된 경계

| 담당 | 하는 일 | 이유 |
|---|---|---|
| **쿼리 (결정론)** | 오늘 복습 대상 목록, 만성 지표 숫자, 최근 창 추출, 복습 단계 전이 | 놓침이 조용히 일어나면 안 된다. 회귀 테스트가 가능하다 |
| **Claude (판단)** | 무엇이 약점의 본질인지, 어떤 질문·상황으로 연습시킬지, 난이도, 지시문 작성 | 점수식으로 산출 불가능한 통찰이다. 생성은 LLM만 한다 |
| **Nova (응대)** | 실시간 대화 | Claude를 음성 턴 동기 경로에 넣지 않는다 (`PRD.md:112`) |

**임계값을 발명하지 않는다.** 만성 여부·우선순위 같은 판정을 우리가 숫자로 정하지 않고, 쿼리는 **사실만** 제공하고 Claude가 판단한다. 예외는 복습 주기(1·3·7일)와 재시도 상한처럼 이미 문서로 확정된 값뿐이다.

### 3.3 계획이 없을 때 — 학습이 막히지 않는다

첫 세션, 계획 생성 실패(`attempts` 5회 소진), 계획 스키마 검증 거부 — 세 경우 모두 **`learning_scenarios`에서 학습자 수준에 맞는 행을 골라 시작한다.** 계획 부재가 학습 중단으로 이어지지 않는다. 이때 `learning_sessions.learning_source`는 `recommended`를 유지하되 계획 미사용 사실을 `session_plans` 부재로 판별한다.

### 3.4 지연 예산 — 사용자가 기다리는 경로에 Claude 호출이 없다

캡틴 질문(2026-08-25): "Claude가 만들고 Nova가 대답하면 느리지 않은가."

| 경로 | Claude 호출 | 체감 |
|---|---|---|
| 세션 시작 | **없음** — `session_plans` 1행 조회 + 지시문 전달 | DB 조회 1회 |
| 세션 중 대화 | **없음** — Nova 단독 | Nova 자체 지연만 |
| 턴마다 분석 | 있음 (비동기 job) | 0 — 음성 응답 경로 밖 (Phase 1 §5.1) |
| 계획 생성 | 있음 | 0 — **직전 세션 종료 시** 미리 실행 (§3.1) |

**결론: 추가 아키텍처가 필요하지 않다.** 계획을 세션 시작이 아니라 앞선 세션 종료에 붙인 것이 이 문제의 해법이고, Phase 1이 분석을 음성 경로에서 떼낸 것과 같은 구조다.

**남는 틈 1건 — 지연이 아니라 기능 퇴화다.** 세션을 끝내고 곧바로 다시 시작하면(예: "추가 학습" 연속 실행) 계획 생성이 아직 끝나지 않아 폴백으로 시작된다. 느려지는 것이 아니라 패턴 기반 선택이 조용히 꺼진다. 보완책은 §11 이월에 둔다(캡틴 결정: 이후 과제).

**지금 반영하는 값싼 조치 1건**: 지시문 가변부(§5.2)에 **크기 상한**을 둔다. 지시문이 길어지면 Nova 세션 초기화가 느려질 수 있다. 상한 초과 시 초점 패턴 수와 상황 목록을 먼저 줄인다. 구체 수치는 Phase 2 실연동에서 Nova 초기화 시간을 실측해 정한다 — 지금 숫자를 발명하지 않는다.

**Nova 자체의 응답 지연은 이 설계의 범위 밖이다** — 스텁으로는 측정할 수 없고 Phase 2 실연동에서 계측한다.

## 4. Agent가 받는 입력 — 3계층

전체 이력을 매번 넣지 않는다. 하루 3발화 기준 1년이면 발화 1,000건 수준이라 컨텍스트에는 들어가지만, 매 세션 전량 주입은 비용과 지연을 무의미하게 늘린다.

### 4.1 오늘 다뤄야 하는 목록 (놓치면 안 되는 것)

```sql
select p.* from error_patterns p
 where p.user_id = $1 and p.next_review_at <= clock_timestamp()
 order by p.next_review_at
```

시각은 `clock_timestamp()`를 쓴다 — Postgres `now()`는 트랜잭션 고정이라 시간 기반 판정이 무력화된다(Phase 1 §5.4에서 실측 확인).

**누가 `next_review_at`을 쓰는가 — 이 설계가 정한다.** 현재 이 컬럼에 값을 넣는 코드가 없어(§2) 위 쿼리가 항상 0행을 돌려주므로, 쓰기 주체를 여기서 확정한다.

- **분석 결과 저장 트랜잭션**(Phase 1 §5.2의 replace)에서 함께 갱신한다. 새 패턴이면 `발화 시각 + 1일`, 이미 있는 패턴이 다시 발생하면 복습 단계를 **되돌린다**(1일로 재설정) — 다시 틀린 패턴을 7일 뒤로 미루면 복습의 의미가 없다.
- 복습을 완주하면 다음 단계로 진행한다: 1일 → 3일 → 7일. 3단계를 소진한 뒤 재발하면 1일로 돌아가고, 그 사실이 §6.2의 만성 신호가 된다.
- 단계 자체는 `review_tasks.review_stage`(1~3, `unique(pattern_id, review_stage)`)가 보관한다 — Phase 1이 스키마만 만들어 둔 테이블을 이 설계가 처음 사용한다.
- 세 단계를 모두 통과하고 재발하지 않은 패턴은 `next_review_at`을 null로 두어 목록에서 빠진다. `mastery_score`가 그 상태를 기록한다(§7).

이 갱신은 **쿼리(결정론) 담당이다** — §3.2의 경계에 따라 Claude에게 묻지 않는다. 1·3·7일은 이미 문서로 확정된 값이라 발명이 아니다.

### ✅ 구현이 채운 공백 3건 (2026-09-04, 슬라이스 1) — 소유자는 `app/services/review.py`다

이 절이 정하지 않아 구현에서 결정해야 했던 것들이다. **뒤집으려면 아래 근거를 반박해야 한다.**

**1. 재발 시 상위 단계 행은 삭제한다** (캡틴 결정 2026-09-03). 위 세 번째 항목이 단계를
`review_tasks.review_stage`에 두는데, 그 표는 `unique(pattern_id, review_stage)`이고
`scenario_context`가 not null이라 "1일로 되돌린다"를 그대로는 구현할 수 없었다. 그래서 재계산은
그 패턴의 행을 **전부 지운 뒤 현재 상태 1행만** 넣는다 — 패턴당 0행 또는 1행이다. 지운 이력이
손실이 아닌 근거: 완주 여부는 `pattern_attempts`, 재발 여부는 `error_occurrences`에서 언제든
다시 계산된다.

**2. `mastery_score`는 상태 마커다** (캡틴 결정 2026-09-03). 위 네 번째 항목이 "그 상태를
기록한다"고만 했고 공식이 어디에도 없었다. 3단계를 재발 없이 완주하면 `100`, 재발하면 `0`이고
**중간값을 만들지 않는다** — 그래야 §3.2("임계값을 발명하지 않는다")와 충돌하지 않는다.
재발로 `100 → 0`이 되어도 정보를 잃지 않는다: 완주 이력이 `pattern_attempts`에 남는다.

**3. "복습을 완주하면"에는 간격 조건이 있다.** 위 두 번째 항목을 "정답 3번"으로 읽으면
학습자가 **같은 세션에서 세 번 맞히는 것으로 1·3·7일을 한 번도 경과하지 않고** 완주한다 —
간격 반복 자체가 무의미해진다(2026-09-03 계획 검토에서 잡아 실제로 재현했다). 그래서 구현은
정답 횟수를 세지 않고 **예정일을 하나씩 접는다**: 그 단계의 `next_review_at`이 온 **뒤에** 맞힌
정답만 단계를 올린다. 완주까지 최소 **1+3+7 = 11일**이 실제로 경과한다. 이 읽기가 이 절의
`next_review_at <= clock_timestamp()` 판정과도 정합한다.
반대로 예정일을 **한참 지나** 맞힌 것은 그대로 통과시킨다 — "너무 늦은 복습"의 상한을
발명하지 않는다(§3.2). 늦게 맞히는 쪽이 더 어려운 조건이라 약한 증거일 이유도 없다.
`incorrect` 판정은 occurrence가 없어도 **재발로 작동한다**(모델이 오류를 findings에 넣지 않고
attempts에만 적은 경우를 덮는다).

**4. 발음 카테고리는 이 스케줄에 들어오지 않는다 — 슬라이스 1의 기록되지 않은 축소였다.**
2026-09-04 코드 리뷰가 세 겹으로 막혀 있음을 확인했다: ① `recompute`의 호출자는 분석 워커

### 4.2 최근 창

### 4.4 발음 시도 (2026-08-27 추가 — `PRD.md` v1.1 R11-9)

자매 설계(`2026-08-27-pronunciation-echo-design.md`)가 `pronunciation_attempts`에 쌓는 시도를 계획 입력에 포함한다.

```sql
select a.target_sound, a.outcome, count(*) as attempts, max(a.created_at) as last_seen
  from pronunciation_attempts a
  join learning_sessions s on s.id = a.session_id
 where s.user_id = $1 and a.created_at >= $2      -- §4.2와 같은 14일 창
```

**주의 2가지.**

발음도 초점 패턴이 될 수 있으므로 §5.1의 초점 패턴 1~2개 안에 들어간다. 발음만 2개를 고르는 것을 금지하지 않는다 — 그 판단도 Claude 몫이다.

## 6. 만성 약점 산정 — 숫자는 계산, 통찰은 노트

### 6.1 숫자 — 새로 저장할 것이 없다 (실측 확인)

아래 지표는 기존 테이블만으로 계산된다. 2026-08-25에 실제 DB에 쿼리를 돌려 확인했다.

```sql
select p.id, p.pattern_key, p.category, p.frequency,
       count(distinct u.session_id)                                   as recurring_sessions,
       count(distinct (u.created_at at time zone $2)::date)           as recurring_days,
       min(u.created_at)                                              as first_seen,
       max(u.created_at)                                              as last_seen,
       max(u.created_at) - min(u.created_at)                          as span
  from error_patterns p
  join error_occurrences eo on eo.pattern_id = p.id
  join utterances u        on u.id = eo.utterance_id
 where p.user_id = $1
 group by p.id
```

**함정 (실측으로 확인) — `error_patterns.created_at`을 지속 기간의 시작으로 쓰면 안 된다.** 라이브 DB에서 `last_seen_at - created_at`이 **음수(-3.8초)** 로 나왔다. 패턴 행의 insert 시각과 발화 시각이 서로 다른 출처이기 때문이다. 지속 기간은 반드시 **발화 시각(`utterances.created_at`)의 min/max**로 계산한다. Phase 1 §6.5가 `last_seen_at`을 발화 시각 기준으로 정한 것과 같은 이유다.

**휴면 후 재발(최대 공백)** 은 같은 패턴 occurrence의 발화 시각 배열에 `lag()`를 걸어 인접 간격의 최대값으로 얻는다. `frequency=5`가 하루에 몰린 것과 3개월에 걸쳐 흩어진 것은 완전히 다르고, 그중 **한동안 사라졌다가 다시 나온 것**이 가장 위험한 신호다.

산정 방식은 **조회 시 계산(뷰 또는 쿼리 함수)** 으로 둔다. 롤업 테이블을 두는 안은 채택하지 않았다 — 단일 사용자 규모에서 결과가 같고 갱신 시점·신선도 관리만 늘어난다(YAGNI).

### 6.2 만성 판정을 우리가 하지 않는다

임계값(재발 며칠 이상이면 만성인가)을 이 설계가 발명하지 않는다. **쿼리는 위 숫자를 사실로 제공하고, 만성 여부와 우선순위는 Claude가 판단한다.** §3.2의 승인된 경계를 따른다.

단 하나의 결정론적 신호는 문서로 이미 확정된 것에서 유도한다 — **복습 3단계(1·3·7일)를 모두 소진한 뒤에 다시 발생한 패턴**은 사실 자체로 만성이므로 그 여부를 계산해 함께 넘긴다.

⚠️ **이 신호를 계산해 Claude에 넘기는 것은 슬라이스 2다.** 슬라이스 1의 만성 지표
쿼리(`app/services/chronic.py`)는 §6.1의 숫자만 돌려주고 이 신호를 포함하지 않는다 —
§12.1이 슬라이스 1에 §6.1만 배정했기 때문이다. **정보는 잃지 않는다**: 슬라이스 1의
`mastery_score`가 재발로 `100 → 0`이 되어도 완주 이력이 `pattern_attempts`의 correct 행과
`error_occurrences`에 남아 언제든 재계산된다(§4.1 구현 공백 2번).

### 6.3 Claude 관찰 노트 (`learner_notes`)

숫자가 담을 수 없는 관찰을 보존한다. 예: "짧은 문장에서는 관사를 붙이는데 문장이 길어지면 빼먹는다", "일상 문맥에서는 맞고 업무 문맥으로 옮기면 같은 오류가 재발한다".

- 계획 생성과 **같은 Claude 호출**에서 갱신한다 (호출 1회로 계획 + 노트).
- **덧붙이기만 하고 갱신하지 않는다(append-only).** 최신 행이 현행 노트이고 과거 행은 남는다. 드리프트가 생기면 이전 노트로 되돌릴 수 있고, 노트의 변화 자체를 관측할 수 있다.
- 노트가 참조한 창(발화 범위)을 함께 적어 어떤 근거로 쓰인 노트인지 추적한다.

## 9. 4 Lenses 검증

### Contract

- **계획 생성 job**: 입력은 종료된 세션 1개의 `session_id`. 출력은 `session_plans` 1행 + `learner_notes` 1행 + `users.current_level` 갱신이 **한 트랜잭션**. 부분 반영을 남기지 않는다.
- **세션 시작**: `session_plans`가 있으면 그것을, 없으면 폴백을 쓴다. **반환은 항상 성공한다** — 계획 부재가 세션 시작 실패로 번역되지 않는다.
- **`session_plans` 불변조건**: `focus_pattern_ids` 길이 1~2, `questions` 길이 3~5, `reason` 비어 있지 않음.
- **`learner_notes` 불변조건**: 갱신·삭제하지 않는다. 최신 `created_at` 행이 현행이다.
- **어댑터 포트**: `start(instruction)`은 지시문을 **소비만** 한다. 어댑터가 세션·DB 상태를 바꾸지 않는다.

### Boundary

- **타입 경계**: Claude 출력(JSON) → `session_plans`/`learner_notes` 행. 신뢰할 수 없는 외부 데이터로 취급해 저장 전 스키마 검증한다(Phase 1 W7 방식 재사용). `target_level`이 CEFR 값역 밖이면 거부, 두 단계 도약이면 거부.
- **시간 경계**: 최근 창(§4.2)과 재발 일수 계산의 날짜 단위는 UTC가 아니라 `users.timezone`(`Asia/Seoul`) 현지 날짜다. 모든 시각은 `timestamptz`, naive datetime을 만들지 않는다. 시간 기반 판정은 `clock_timestamp()`.
- **프로세스 경계**: 계획은 세션 종료 시 만들어 다음 세션 시작에서 읽는다 — 그 사이 프로세스가 죽어도 job이 큐에 남아 이어진다.
- **학습/명령 경계**: 계획 입력은 `utterance_type='learning'`만 선택한다(Phase 1 §6.2 D4 규약 계속).
- **수준 경계**: `users.current_level`은 한 단계씩만 이동한다(§7).

### Failure

- **Claude 호출 실패**: `analysis_jobs`의 백오프·상한 5·terminal `failed`를 그대로 쓴다. 계획 없이 다음 세션이 시작되면 폴백(§3.3).
- **스키마 검증 거부**: 계획을 저장하지 않고 job을 `last_error`와 함께 실패 처리한다. 반쯤 검증된 계획을 쓰지 않는다.
- **노트가 잘못 갱신됨**: append-only라 이전 노트가 남아 있다. 되돌리기가 데이터 삭제 없이 가능하다.
- **수준이 잘못 올라감**: 하향을 허용하므로 다음 갱신에서 복구된다. 한 단계 제약이 폭주를 막는다.
- **부분 실행**: 계획·노트·수준 갱신·job 완료가 한 트랜잭션이므로 절반만 반영된 상태가 없다.
- **폴백 뱅크가 비어 있음**: 시드가 보장한다(Phase 1 F1이 시나리오 3행을 시드). 그래도 0행이면 세션은 시나리오 없이 시작한다(`scenario_id` nullable — `app/services/sessions.py`의 현재 계약과 동일).

### Dependency

- **초기화 순서**: 006 마이그레이션(슬라이스 1) → 007(슬라이스 2) → 폴백 뱅크 시드 → 워커 기동. 폴백 뱅크는 슬라이스 2에서 필요해진다. 뱅크 없이 폴백을 호출하면 §Failure의 마지막 경로로 떨어진다.
- **읽기 전 갱신 보장**: 계획은 **앞선 세션 종료 시** 만들어진다. 세션 시작이 계획 생성을 기다리지 않는다 — 기다리면 §3.1의 지연 회피가 무의미해진다.
- **`pattern_attempts` → `mastery_score` 순서**: 정답 여부가 먼저 기록되고 그 다음 갱신이다. 같은 분석 트랜잭션 안에서 처리한다.
- **어댑터 확장의 파급 제한**: `start(instruction)` 변경이 세션 수명·저장·job 등록 로직에 닿지 않아야 한다 — import 그래프 검사(Phase 1 G3 방식)로 강제한다.
- **단독 테스트 가능성**: 계획 생성 job은 Nova 없이 단위 테스트한다. 지시문 전달은 스텁 어댑터의 기록으로 검증한다.

## 10. 수용 시나리오

**AS1 — 복습 목록 누락 없음**
Given 서로 다른 3개 패턴의 `next_review_at`이 모두 과거일 때, When 계획 생성이 돌면, Then 세 패턴 전부가 Claude 입력에 포함된다. 하나라도 빠지면 실패다.

**AS2 — 만성 지표 정확성**
Given 같은 패턴이 3개월에 걸쳐 서로 다른 4개 날짜에 발생하고 중간에 40일 공백이 있을 때, When 만성 지표를 계산하면, Then `recurring_days=4`, 지속 기간이 약 3개월, 최대 공백이 약 40일로 나온다. **지속 기간이 음수가 되지 않는다**(§6.1 함정).

**AS3 — 계획이 이력을 반영**
Given `article` 패턴의 재발 일수가 가장 크고 `next_review_at`이 오늘일 때, When 계획이 생성되면, Then 초점 패턴에 그 패턴이 포함되고 질문 3~5개가 그 패턴을 유발하는 상황을 담으며 `reason`이 비어 있지 않다.

**AS4 — 계획 없이도 학습이 시작된다**
Given 해당 세션의 계획 생성 job이 `failed`일 때, When 사용자가 학습을 시작하면, Then 폴백 시나리오로 정상 시작되고 `session_plans` 행이 없다. 시작이 실패하지 않는다.

**AS5 — 잘못된 계획 거부**
Given Claude가 `reason`이 빈 문자열이거나 `questions`가 2개이거나 `target_level`이 두 단계 위인 계획을 냈을 때, When 저장을 시도하면, Then 스키마 검증에서 거부되고 job이 `last_error`와 함께 실패하며 `session_plans` 행이 생기지 않는다.

**AS6 — 지시문이 대화 상대까지 도달**
Given 계획에 `target_level`과 초점 패턴이 담겼을 때, When 세션이 시작되면, Then 어댑터의 `start()`가 그 지시문을 받고 스텁이 기록한 지시문에 해당 값이 들어 있다.

**AS7 — 수준 상향과 한 단계 제약**
Given 정답률이 충분히 높아 Claude가 상향을 판단할 때, When 갱신이 적용되면, Then `users.current_level`이 **정확히 한 단계** 올라가고 사유가 `learner_notes`에 남는다. 두 단계 도약 출력은 거부된다.

**AS8 — 노트 되돌리기**
Given 노트가 2회 갱신되었을 때, When 최신 노트가 부적절하다고 판단되면, Then 이전 노트 행이 그대로 남아 있어 데이터 삭제 없이 복구할 수 있다.

**AS9 — 연습 상황 저장**
Given Claude 분석이 `suggested_contexts` 3개를 산출할 때, When 결과가 저장되면, Then `error_occurrences.suggested_contexts`에 보존되고 재분석(replace) 후에도 최신 값이 남는다. ✅ **충족 (2026-09-04, 슬라이스 1)** — 006이 컬럼을 신설했고 분석 프롬프트가 상황 3개를 요구하며
저장 경로가 관통했다. 재분석 후 최신 값이 남는 것까지 통합 테스트가 단정한다.
**남은 것은 하나뿐이다**: 실물 Claude가 실제로 이 필드를 내는지 — 자동 테스트는 대역을 쓰므로
판정할 수 없다(계획서의 실물 검증 L2). ~~이 컬럼은 아직 없다~~는 서술은 폐기됐다.

**AS10 — 정답 여부 기록의 멱등성**
Given 같은 재발화에 대한 분석이 재시도될 때, When 결과가 저장되면, Then `pattern_attempts` 행이 중복되지 않는다(`unique(pattern_id, utterance_id)`).

### 10.1 실물 검증 (자동 테스트로 판정 불가한 것)

**AS-live** — 실제 Claude로 계획 생성 1회. 단정: `reason`이 한국어 문장이고, 질문이 초점 패턴을 실제로 유발하는 형태이며, 지시문의 목표 문장 길이대가 `target_level`과 모순되지 않는다. 판정은 사람이 한다(Phase 1 W-live와 같은 방식).

한 계획으로 가면 슬라이스 2의 검증이 합성 데이터에 의존한다. 그것보다 **데이터 유실을 먼저 멈추는 것**이 낫다 — `suggested_contexts`는 지금 산출되고도 저장되지 않아 소급이 불가능하고(§8.2), `next_review_at`은 아무도 쓰지 않아 "오늘 복습할 목록"이 항상 0행이다(4차수 M0-③④로 실측 확인).

| 순서 | 슬라이스 | 완료 판정 |
|:--:|---|---|
| **1** | 기록과 계산 — `suggested_contexts` 저장, `pattern_attempts`, 복습 스케줄 갱신(§4.1), 만성 지표 쿼리(§6.1) | "오늘 복습할 목록"이 처음으로 값을 갖는다. 화면 변화는 없다 |
| **2** | 판단과 적용 — 계획 생성 job, `session_plans`, `learner_notes`, 지시문 전달(§5.2), 수준 갱신(§7) | AS1~AS10 + AS-live |

**자매 설계(발음)와의 순서 관계**: 접합면이 `error_patterns` 한 행이라 강한 제약이 없다. 다만 발음 설계의 003 마이그레이션이 슬라이스 1과 **독립**이므로 병행 가능하다. 슬라이스 2는 발음 시도를 계획 입력에 넣으므로(§4.4) 발음 설계의 기록 경로가 먼저 있으면 검증이 실물 데이터로 된다 — **권고 순서: 슬라이스 1 → 발음 기록 → 슬라이스 2.**
