## §2. 설계 — 두 경로로 가른다

캡틴 노트가 가리키는 요청은 **화자가 이미 세션 안에 있는지**에 따라 서로 다른 메커니즘을
탄다. 섞으면 "진입점"과 "대화 연장"이 같은 문제로 보인다 — 그것이 이 조사가 처음 걸릴
뻔한 자리다.

### 경로 A — 세션이 이미 살아 있을 때 (⚠️ 범위 밖 — 경계만 긋는다)

학습자가 라이브 세션 중 자연어로 "질문 더 주세요"라고 말하는 경우다. 이것은 **진입점이
아니다** — 대화 상대(모델)가 이미 듣고 있으므로 다음 턴에 질문을 더 하는 것으로 충분하고
(`gap-investigation.md:79-86`), §1에서 확인했듯 시스템 프롬프트를 갈아 끼울 수도 없다
(어차피 지금 세션이 이미 로드한 3~5개 질문·초점 패턴 안에서 답해야 한다). 처방은 **대화
규칙 한 줄 추가**로 이미 충분히 싸다고 조사돼 있다.

⛔ **이 처방은 지금 어느 태스크도 소유하지 않는다** — `TASK-6`(드릴 4턴 구조)은 조립
지시·턴 관측만 다루고 이 문장을 다루지 않는다(`TASK-6` AC 3건·Implementation Notes 직접
확인). §6에 범위 밖 발견으로 남긴다.

### 경로 B — 세션 밖에 있을 때 (AC#2·#3이 답할 자리)

학습자가 지금 라이브 세션에 있지 **않고**(세션 종료 후 결과 화면·대시보드 등), 스케줄된
다음 추천 세션을 기다리지 않고 지금 바로 드릴을 하나 더 하고 싶은 경우다. AC#1이 확인한
"경로 0곳"은 이 경우를 가리킨다 — 세션을 새로 여는 진입점이 없다는 뜻이다.

## §3. AC#2 판정 — 진입 방식

**결론: 새 버튼·새 진입점을 만들지 않는다. `Additional Learning`의 기존 다섯 메뉴 중
`질문 답변 5개` 항목을 그대로 쓴다** (`docs/PRD.md:75`).

**음성 이연 결정과 충돌하지 않는 근거**: `Voice Control` 절 자체가 "UI 버튼과 동일한
행동을 음성 명령으로 수행"이라고 원칙을 못박았다(`:81`) — 버튼이 **1차 수단**이고 음성
명령은 그 위에 얹는 미러다. 3단계로 이연된 것은 **미러(명령 인식·제어 모드 버튼·확인
단계)**이고, 버튼 그 자체는 애초에 phase 1의 몫이었다. 그래서 이 결정은 이연을 우회하는
편법이 아니라 **PRD가 원래 의도한 1차 경로를 그대로 쓰는 것**이다.

### 즉시 드릴에 고유한 결정 3개

**1. 어느 계획의 질문을 쓰나** — 새로 만들지 않는다. 세션 생성이 항상 호출하는
`load_prepared_plan`(사용자 최신 1건)을 **그대로** 재사용한다. 즉시 드릴 진입이 계획
생성 워커(글 모델 왕복)를 새로 트리거하지 않는다 — R11-4("계획 생성 워커를 대기 경로에
두지 않는다")를 그대로 지킨다. 부수 효과: 직전 세션의 `plan_next_session` job이 아직
끝나지 않았으면 그 세션과 **같은 계획**을 다시 읽는다 — 이것은 새로 만드는 문제가 아니라
기존 설계가 이미 받아들인 경계다(`sessions.py:119-123` 주석, "같은 계획이 두 세션에
연속으로 쓰일 수 있다").

**2. 기대값(`drill_turns_expected`)을 어떻게 다루나** — 특별 취급하지 않는다. 계획이
있는 모든 세션에서 이미 자동으로 계산·저장되므로(§1), 즉시 드릴 세션도 **같은 공식,
같은 시점**에 같은 값을 받는다. 늘리지도 줄이지도 않는다. ⚠️ 이 선택이 관측 신호에
미치는 영향은 §7이 별도로 다룬다 — 계산이 같다는 것과 "신호가 오염되지 않는다"는 것은
다른 주장이다.

**3. 세션 안인가 새 세션인가** — **새 세션**이다. 근거 셋: ① 시스템 프롬프트가 생성자
인자로 굳고 갈아 끼울 경로가 없다(§1) ② 경로 A(세션 안 요청)는 애초에 이 태스크의 범위가
아니다 ③ AC#1이 "경로 0곳"으로 확인한 대상 자체가 "세션을 새로 여는" 진입점이다. 새
세션은 기존 `create_session` 흐름을 **그대로** 탄다 — 시나리오 블록·계획 블록·드릴 줄이
있으면 붙고 없으면 빠지는 기존 계약(`nova.py` 조립 규약)과 동일하다. `mode`는 기존 값
`'speaking'`을 쓴다 — 새 값을 만들지 않는다(§1, 값역 확인).

## §4. AC#3 판정 — 구현 슬라이스

**백엔드 메커니즘은 이미 구현 대상에 포함돼 있다 — TASK-7이 새로 만들 것이 없다.**
즉시 드릴이 필요로 하는 것(질문 재사용·`drill_turns_expected` 자동 계산·기존 `mode`
재사용)은 전부 `TASK-6`·`TASK-25`의 설계(`2026-09-07-scenario-and-drill-turns-design.md`
§6, 16곳)가 이미 정의했고, 지금 이 세션에서 Batch A/B/C로 구현이 진행 중이다(직접 확인한
`drill_count=5` 기본값이 그 진행의 증거다).

**남는 것은 진입 배선 하나뿐이다**: `Additional Learning` 메뉴의 `질문 답변 5개` 항목이
눌렸을 때 기존 세션 생성 API를 호출하는 것. 이 배선은 **`TASK-10`이 추가 학습 진입점을
구조화한 뒤, 그 구조 안에서 함께 구현한다** — `TASK-7`은 별도 구현 슬라이스를 새로 만들지
않는다. `TASK-10`이 `TASK-2`(일일 권장량) 대기로 막혀 있으므로, 이 배선도 같은 선행을
공유한다(새로운 의존이 아니라 이미 있는 의존을 물려받는 것이다).

## §5. `TASK-10`에 넘기는 요구 목록

`TASK-10`이 추가 학습 진입점을 구조화할 때 아래를 반영해야 한다 — 즉시 드릴이 그 구조에
거는 요구다. **값·배치를 대신 정하지 않고 요구만 남긴다.**

1. **`질문 답변 5개` 메뉴 항목은 새 세션 생성이다** — 시나리오·계획 로드를 포함한 기존
   `create_session` 흐름을 그대로 호출한다. 별도의 "드릴 전용" 세션 변형(시나리오 생략
   등)을 만들 필요가 없다(근거: §3-3, §7 유도 2).
2. **`learning_source` 값 후보 둘 다 이 용도에 들어맞는다 — 최종 선택은 `TASK-10`이
   한다.** `user_requested`(사용자가 메뉴에서 명시적으로 고름)와 `additional`(추천 밖
   학습)이 둘 다 근거가 있다: PRD는 5개 메뉴 항목 전체를 "추가 학습"으로 묶으면서도
   "추천 과제와 자유 과제를 구분해 번아웃 분석에 쓴다"(`PRD.md:76`)고만 하고, 5개 항목
   사이의 세분을 규정하지 않는다. **새 값은 필요 없다** — 이미 열린 셋 안에서 고르면
   된다.
3. **`started_via='ui'`를 쓴다** — 이 항목은 버튼(메뉴 탭)으로만 진입한다. 음성 명령
   미러가 3단계에 들어오면 그때 `voice_command`가 같은 자리에 추가된다(지금은 아니다).
4. **다섯 메뉴 항목 중 하나가 이미 정확히 지금 드릴 메커니즘과 일치한다는 사실을
   구조화에 반영한다** — `drill_count` 기본값 5(캡틴 결정 17)가 "질문 답변 5개"라는
   이름과 우연이 아니라 대응 관계다. 구조화 문서가 이 대응을 명시하면 다음 사람이
   "왜 5인가"를 다시 조사하지 않는다.

## §6. 범위 밖 발견 (내 몫이 아니지만 보고한다)

**세션 안 자연어 요청("질문 더 주세요")의 처방이 소유자가 없다.** `gap-investigation.md`
항목 10이 처방(대화 규칙 한 줄 추가)까지 적어 뒀지만, `TASK-6`은 그 문장을 다루지 않고
검토한 결과 다른 어느 태스크도 소유하지 않는다(§2 경로 A). 싸게 닫을 수 있는 항목이 원장에
없어 다음에 또 "0곳"으로 재조사될 위험이 있다 — 팀리드가 `TASK-6`에 AC를 추가할지, 새
태스크를 만들지 판단해야 한다.

## §7. 기대값 관측(`drill_turns_expected`)과의 맞물림

**결론: 즉시 드릴은 기대값 공식을 바꾸지 않지만, 집계 신호를 오염시킬 위험이 있다 —
세그멘테이션이 필요하다.**

계획이 있는 모든 세션이 같은 공식으로 기대값을 받으므로(§3-2), 즉시 드릴 세션 자체가
"미달"을 더 자주 내도록 설계돼 있지는 않다. 그러나 **캡틴 결정 10**은 "집계된 미달을
지시문을 고치는 입력으로 쓴다"고 명시한다(`captain-decisions.md:175`). 즉시 드릴은 사용자가
메뉴에서 명시적으로 고른, 목적이 좁은 세션이다 — 원하는 것을 얻으면 세션을 일찍 끝낼
가능성이 추천 세션(더 넓은 대화가 이어지는 것을 전제)보다 높다. 이 차이가 실제로 존재한다면
`learning_source`별 미달률이 갈릴 수 있고, 그것을 구분하지 않고 전체를 뭉쳐 집계하면
"모델이 지시를 안 지켰다"와 "이 세션 종류는 원래 짧게 끝난다"를 구분하지 못한 채 지시문을
고치는 잘못된 근거가 될 수 있다.

⚠️ **지금은 관측 배관이 세션당 로그 한 줄뿐이고 집계 job이 아직 없다**
(`scenario-and-drill-turns-design.md` §2.3의 "로그: 미달이면 warning 한 줄" — 세션 단위
경고이지 집계가 아니다). 그래서 지금 당장 세그멘테이션을 구현할 자리가 없다 — **이후 누군가
그 집계를 만들 때 `learning_source`로 나눠 보라는 요구만 남긴다.** 즉시 드릴 자체의 설계를
바꿔 이 위험을 막을 필요는 없다(공식은 그대로 두는 것이 §3-2의 결론이다).

| 1 | 즉시 드릴은 **새 세션**이다(경로 A와 분리) | 세션 안에서 시스템 프롬프트를 갈아 끼우는 메커니즘을 새로 만든다 → `factory.py`·`nova.py`에 "런타임 재조립" 경로가 생기고, 지금 없는 상태 관리(현재 세션이 무슨 질문을 이미 썼는지)가 필요해진다. 비용이 크고 지금 근거가 없다. |
| 2 | "드릴 전용" 세션 변형을 만들지 않고 **기존 `create_session` 흐름을 그대로** 쓴다(시나리오 포함) | 시나리오·잡담을 생략하는 짧은 변형을 만든다 → 진입점마다 다른 조립 로직이 생겨 `nova.py`의 "넷 다 없으면 `SYSTEM_PROMPT` 그 자체" 같은 단순한 계약이 진입점별로 갈라진다. 사용자가 "5문항만 빨리 하고 싶다"는 요구를 더 잘 만족시킬 수는 있다. |
| 3 | `mode`는 새 값 없이 `'speaking'`을 쓴다 | 드릴 전용 `mode` 값을 추가한다 → 값역이 넓어지고 `mode`를 읽는 모든 코드가 새 값을 처리해야 한다. 지금 그 필요가 없다(값역은 진입 방식이 아니라 대화 형태를 가리킨다). |
| 4 | 계획은 **재사용**하고 새로 생성하지 않는다 | 즉시 드릴 진입 시 계획 생성 워커를 동기 호출한다 → R11-4를 어기고, 사용자가 버튼을 눌렀는데 글 모델 왕복을 기다려야 하는 대기 경로가 생긴다. |
