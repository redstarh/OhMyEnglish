# 데이터 우선 설계 규약 (Data-First Design)

> **정본 지침이다.** 캡틴 지시 2026-09-06: *"진행 간 필요한 테이블은 기존 테이블 스키마를 확인하고,
> ALTER 할지 CREATE 할지 판단해서 진행해. 코드만 있고 저장이 안 되어 이후 프로세스가 끊기지 않도록
> 설계해. 필요 table을 먼저 검토하고, 저장될 데이터를 기반으로 코드를 설계해. 무작정 개발에
> 들어가지 말고, 데이터·테이블·설계가 정합성이 맞는지 판단하고 진행해."*
>
> **적용 범위**: 이 리포의 **모든** 신규 요구사항·설계 보강 태스크. 코드를 한 줄 쓰기 전에 이 순서를
> 지킨다. 예외는 없다 — 문서 전용 태스크는 애초에 표를 만들지 않으므로 대상이 아니다.
>
> **왜 이 규약이 생겼나**: 이 리포는 같은 실패를 **네 번** 냈다 — 값을 만들어 저장까지 하고
> **읽는 코드가 0곳**인 자리가 넷이었다(계획이 만든 질문 · 다시 연습할 상황 · 복습 과제 행 ·
> 시나리오). 근거는 `docs/design/2026-09-06-gap-investigation.md` §1이다.
> 그 반대 방향의 실패도 있다 — 결정은 기록됐는데 **구현이 착지하지 않은** 것
> (`daily_goal_minutes`를 "앱 상수로 대체했다"고 적었으나 그 상수가 없다).

---

## 1. 순서 — 이 순서를 바꾸지 않는다

| # | 단계 | 산출물 | 넘어가는 조건 |
|--:|---|---|---|
| 1 | **기존 스키마 확인** | 이미 있는 표·컬럼·값역·제약 목록 | **직접 조회**로 확인했다(파일만 읽지 않는다) |
| 2 | **ALTER 대 CREATE 판정** | 판정 + 근거 | 아래 §2의 판정 기준을 적용했다 |
| 3 | **저장될 데이터를 먼저 적는다** | 표 정의 + **예시 행 1~2개** | 그 행이 실제 요구사항을 만족하는지 눈으로 확인했다 |
| 4 | **읽는 쪽을 함께 정한다** | 소비자 목록(화면·프롬프트·쿼리) | **소비자가 0곳이면 진행하지 않는다** (§3) |
| 5 | **정합성 판정** | 데이터 ↔ 표 ↔ 설계 대조 결과 | 세 층이 서로 모순하지 않는다(§4) |
| 6 | 코드 작성 | — | 1~5가 끝났다 |

⚠️ **1~5를 건너뛰고 6으로 가지 않는다.** "무작정 개발에 들어가지 마라"가 이 규약의 한 문장 요약이다.

---

## 2. ALTER 대 CREATE 판정 기준

**먼저 조회한다. 파일만 읽고 판단하지 않는다** — 스키마 파일과 실제 DB가 갈라져 있을 수 있다
(실측: 개발 DB에 007이 미적용이라 `session_plans`가 **파일에는 있고 DB에는 없었다**).

```bash
# 표 목록
psql -U ohmy -d ohmyenglish -tAc "select tablename from pg_tables where schemaname='public' order by 1;"
# 특정 표의 컬럼
psql -U ohmy -d ohmyenglish -tAc "select column_name,data_type,is_nullable,column_default
  from information_schema.columns where table_name='<표>' order by ordinal_position;"
# 제약(값역 포함)
psql -U ohmy -d ohmyenglish -tAc "select conname,pg_get_constraintdef(oid)
  from pg_constraint where conrelid='<표>'::regclass order by conname;"
# 적용 이력
psql -U ohmy -d ohmyenglish -tAc "select filename from schema_migrations order by filename;"
```

| 상황 | 판정 | 주의 |
|---|---|---|
| 그 개념을 담을 표가 **없다** | **CREATE** | 새 표는 위험이 낮다 — 없던 것이 생길 뿐이다 |
| 표는 있고 **컬럼만 없다** | **ALTER ADD COLUMN** | `NOT NULL`을 바로 걸지 않는다 — 기존 행이 채울 값이 없다. 기본값을 주거나 nullable로 만든 뒤 채운다 |
| **값역(CHECK)에 항목을 더한다** | **ALTER: DROP → ADD** | ⚠️ **가장 위험한 형태다.** 이미 데이터가 든 표의 규칙을 바꾼다. 되돌리기 스크립트를 함께 쓴다 |
| 값역이 **이미 열려 있다** | **아무것도 하지 않는다** | 실측 사례: `task_type`·`category`·`mode`가 이미 `shadowing`을 허용한다. 값역을 다시 넓히지 마라 |
| 컬럼이 **있는데 아무도 쓰지 않는다** | **재사용한다** | 실측 사례: `learning_source`·`audio_url`이 그렇다. **새 컬럼을 만들지 마라** |

**마이그레이션 번호**: 적용은 **파일명 정렬 순서**다(`scripts/migrate.py`가 `sorted(glob("*.sql"))`을
돈다). **비어 있는 과거 번호를 되살리지 않는다** — 이미 적용된 번호보다 앞으로 정렬되어 새 DB와
기존 DB의 적용 순서가 갈라진다. **항상 다음 빈 번호를 쓴다.**

## 3. "코드만 있고 저장이 안 되어 이후 프로세스가 끊긴다" — 이 규약의 핵심

캡틴이 지목한 실패는 **양방향**이다. 둘 다 막는다.

| 방향 | 증상 | 판별 질문 |
|---|---|---|
| **A. 저장은 되는데 읽는 곳이 없다** | 값이 쌓이지만 아무 동작도 바뀌지 않는다. 판정이 영원히 `부분`에 머문다 | **"이 값을 읽는 코드가 몇 곳인가?"** 0이면 진행하지 않는다 |
| **B. 코드는 있는데 저장할 자리가 없다** | 계산은 되지만 다음 단계가 받을 것이 없어 끊긴다 | **"이 값이 프로세스를 넘어가려면 어디에 남아야 하나?"** 답이 없으면 표부터 정한다 |

**착수 전에 이 표를 채운다. 빈칸이 있으면 코드를 쓰지 않는다.**

| 항목 | 답 |
|---|---|
| 무엇을 저장하나 | |
| 어느 표·컬럼에 | |
| **누가 읽나** (파일:심볼 또는 "이 태스크에서 만든다") | |
| 읽은 값으로 **무엇이 달라지나** (화면·프롬프트·판정) | |
| 읽는 쪽이 아직 없다면 **어느 태스크가 소유하나** | |

⚠️ **마지막 줄이 비면 그것이 다섯 번째 "reader 0곳"이 된다.** 소유자 없는 값은 만들지 않는다.

## 4. 정합성 판정 — 세 층을 대조한다

코드를 쓰기 전에 **데이터 · 표 · 설계**가 서로 모순하지 않는지 본다.

| 대조 | 물어볼 것 | 실패 사례 (이 리포에서 실제로 났다) |
|---|---|---|
| **요구사항 ↔ 표** | 요구사항이 요구하는 값을 표가 담을 수 있나 | 계획이 질문 3~5개를 만드는데 **지시문 자료구조에 질문 필드가 없다** → 전달 불가 |
| **표 ↔ 코드** | 표에 있는 컬럼을 코드가 읽나 | `scenario_id`를 저장하지만 **select가 0곳** → 고른 시나리오가 대화에 도달하지 않는다 |
| **설계 ↔ 실제 DB** | 설계서가 있다고 적은 것이 DB에 실제로 있나 | 설계서가 **없는 컬럼을 있는 것처럼** 서술한 적이 있다 |
| **결정 ↔ 구현** | 기록된 결정이 코드에 착지했나 | `daily_goal_minutes`를 "앱 상수로 대체했다"고 적었으나 **그 상수가 없다** |

**하나라도 어긋나면 코드를 쓰지 않고 그 어긋남을 먼저 보고한다.**

## 5. 되돌리기 어려운 변경의 절차 (§2의 위험 형태)

값역 변경·`NOT NULL` 추가처럼 **이미 있는 데이터를 건드리는** 마이그레이션은 아래를 지킨다.

1. **적용 전 백업을 파일로 뜬다.** 되돌릴 수단을 손에 쥔 상태에서만 적용한다.
2. **적용 전 행 수를 전 표에 대해 기록한다.**
3. 적용한다.
4. **적용 후 다시 조회해 대조한다** — 새 표가 생겼는지 + **기존 행 수가 하나도 줄지 않았는지**.
5. 어긋나면 **백업으로 되돌린다.**
6. 되돌리기 스크립트를 함께 만드는 것이 원칙이다. 못 만들면 **그 사실을 태스크에 남긴다.**

⚠️ **공유 인스턴스 주의**: PostgreSQL 인스턴스를 다른 프로젝트와 공유한다. **재시작·`ALTER SYSTEM`·
`ALTER DATABASE ... SET TimeZone`을 걸지 않는다.**

⚠️ **공유가 인스턴스 수준이 아니라 스키마 수준이다 (2026-09-06 실측)** — 같은 데이터베이스
`ohmyenglish` 안에 **En-Coach의 `en_coach` 스키마가 함께 있다.** 소유자가 다르다(`en_coach` 역할 대
`pg_database_owner`). 우리 것은 **`public` 스키마 하나**다.

- **`pg_dump`를 스키마 범위 없이 돌리면 실패한다** — 007 적용 전 백업에서 실제로 막혔다:
  `permission denied for schema en_coach`. 우리 역할 `ohmy`에 그 스키마 권한이 없어서 전체 덤프의
  `LOCK TABLE`이 거부된다.
- **반드시 `-n public`을 붙인다**: `pg_dump -U ohmy -d ohmyenglish -n public -f <파일>`.
- **백업이 실제로 데이터를 담았는지 확인한다** — `CREATE TABLE` 수와 `COPY public` 수가 표 개수와
  일치해야 한다(007 백업에서 각각 14로 표 14개와 일치함을 확인했다). 빈 덤프를 백업으로 믿으면
  되돌릴 수단이 없는 채로 적용하게 된다.
- **"우리 DB 하나만 건드린다"가 아니라 "우리 스키마 하나만 건드린다"**로 읽는다.

### 007 적용 실적 (이 절차가 실제로 통과한 형태 — 2026-09-06)

| 단계 | 결과 |
|---|---|
| 백업 | `public` 스키마 덤프 1개(`CREATE TABLE` 14 · `COPY` 14 — 표 개수와 일치) |
| 적용 전 행 수 | 10개 표 기록 |
| 적용 | `scripts/migrate.py` — **파일마다 트랜잭션으로 감싸므로 실패 시 자동 롤백**된다(코드 확인) |
| 적용 후 | 이력에 `007` 추가 · 표 **14 → 16**(`session_plans`·`learner_notes` 신설) · `analysis_jobs`의 작업 종류 값역에 `plan_next_session` 추가됨 |
| **행 수 대조** | **차이 0건** — 기존 데이터 손실 없음 |
| 게이트 | 자동 검사 582건 통과 |

⚠️ **명령의 종료 코드로 성공을 판단하지 않았다** — `migrate.py` 실행이 출력을 내지 않았고 종료 코드
캡처도 비었다. **DB를 직접 조회한 것이 유일한 증거다.** 이것이 §1 1단계의 "직접 조회로 확인했다"가
뜻하는 바다.

## 6. 시각·날짜를 담을 때 (모든 표에 적용)

전역 규약을 그대로 계승한다 — 이 리포에서 실제로 사고가 났던 자리다.

- **이벤트 시각은 `timestamptz`다.** naive `timestamp` 컬럼을 만들지 않는다.
- **"오늘·어제·일일 집계" 같은 달력 날짜는 `current_date`로 구하지 않는다.** 사용자 타임존으로
  변환해 구한다. 타임존의 정본은 **`users.timezone` 컬럼**이다.
- **저장된 `timestamptz`를 변환해 UPDATE하지 않는다.** 표시가 틀렸다고 값을 고치면 실제 순간이
  이동한다 — 되돌릴 수 없다. 변환은 **읽을 때만** 한다.

⚠️ **실측 근거**: UTC 자정~오전 9시(한국 시각) 구간에는 `current_date`가 한국 날짜보다 **하루
이르다.** 쉐도잉의 "당일 경과 삭제"가 이 한 칸에 걸린다 — 하루 일찍 돌면 학습자가 아직 비교하지
못한 녹음이 사라진다.
