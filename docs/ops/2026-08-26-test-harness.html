3tmux 조작 — 이 하네스가 쓰는 만큼

요구사항은 하나다: 다른 에이전트가 돌고 있는 화면에 프로그램이 메시지를 꽂아 넣을 수 있어야 한다. 그게 되면 지시와 통보가 같은 수단으로 처리된다.

주소 표기

tmux에서 터미널 하나를 가리키는 것은 <세션>:<윈도>.<페인>이다. Orca의 term_<uuid> 핸들과 달리 앱 재시작으로 무효화되지 않지만, 세션이 죽으면 사라진다. 페인 제목을 키로 삼지 않는다 — 에이전트가 자기 작업 요약으로 제목을 갱신하므로 붙인 이름이 유지된다는 보장이 없다. 

tmux display-message -p '#{session_name}:#{window_index}.#{pane_index}'   # 자기 주소
tmux list-panes -a -F '#{session_name}:#{window_index}.#{pane_index} #{pane_current_command}'

보내기 / 읽기

# 보내기 — Enter를 빼면 타이핑만 되고 실행되지 않는다.
tmux send-keys -t omy_runner:0.0 '<지시 한 줄>' Enter

# 읽기 — history-limit이 50000이라 넉넉하다.
tmux capture-pane -p -t omy_runner:0.0 -S -300

받는 쪽이 셸이면 텍스트가 셸 명령이 되고, claude 같은 대화형 화면이면 그 에이전트에게 가는 사용자 프롬프트가 된다. 그래서 보낼 대상이 셸인지 에이전트인지 먼저 확인한다. -t를 생략하면 자기 자신이 대상이 될 수 있으므로 항상 명시한다.

화면은 대화 기록이 아니다

capture-pane은 스피너와 상태바가 줄의 대부분을 차지하고, 같은 자리를 덮어 그린 결과가 복원되지 않는다. 화면 읽기는 "지금 무슨 상태냐"를 보는 용도이고, 판정 근거는 러너가 쓴 증거 파일과 CDP 자동 캡처 파일이다. Stop 훅 payload에는 transcript_path가 실려 오므로(6절) 전체 대화가 필요하면 그 JSON을 읽는다.

대기 명령을 쓰지 않는다

tmux wait-for나 sleep 폴링을 쓰지 않는다. 살아 있는 대화형 러너는 끝나지 않으므로 종료 대기는 타임아웃까지 매달리고, 유휴 판정은 "아직 일을 시작하지도 않은 상태"에 즉시 만족돼 완료로 오해하게 만든다. 완료 신호는 6절의 콜백으로 받는다.

권한 한 가지

통보 대상이 orchestrator 자기 세션의 페인이므로 Claude Code의 auto mode는 이 배선을 self-drive로 막을 수 있다. 대화 중 구두 승인으로는 풀리지 않는다 — 세션을 bypass permissions로 두고 배선한다. 다른 세션으로 보내는 send-keys와 capture-pane은 이 기계에서 실행 확인됐다.

5격리 정책 — 공유 dev DB를 되돌리는 방법

하네스는 캡틴의 dev 데이터와 같은 DB에서 돈다. 그래서 "무엇을 오염시키는지"와 "어떻게 정확히 되돌리는지"를 먼저 못 박는다.

오염 지점 3개 — 스키마에서 도출

대상왜 오염되나되돌리는 방법
learning_sessions ·
utterances ·
analysis_jobs ·
error_occurrences		 하네스가 만든 세션에만 달려 있다 세션 삭제로 전부 사라진다. 001 스키마의 on delete cascade가 learning_sessions → utterances → {error_occurrences, analysis_jobs}로 이어진다
error_patterns 여기가 진짜 문제다. unique (user_id, pattern_key) — 세션이 아니라 사용자에 붙는다. 고정 사용자 1명이므로 하네스 실행이 캡틴의 누적 패턴에 섞인다 frequency는 앱이 count(*)로 재계산하고 last_seen_at은 max(u.created_at)이다 (services/analysis.py). 즉 같은 식을 다시 돌리면 원래 값이 정확히 복원된다. 남은 occurrence가 0인 패턴만 삭제한다
실행 중인 백엔드 프로세스 WORKER_ENABLED·voice_adapter가 프로세스 기동 시점에 고정된다 — 런타임 변경 수단이 없다 B계층 시나리오만 :8002를 재기동하고, 시나리오 끝에 baseline 명령 그대로 되돌린다(10절). 프론트는 건드리지 않는다 — 8002라는 주소가 유지되므로 인라인된 NEXT_PUBLIC_API_BASE가 계속 유효하다

부기 테이블 — 하네스가 만든 것만 지우기 위해

파괴적 정리를 "하네스가 만든 세션"으로 좁히려면 그 id 목록이 남아 있어야 한다. 화면이나 타임스탬프 추정으로 좁히지 않는다. 

create table if not exists harness_runs (
  id          uuid primary key default gen_random_uuid(),
  started_at  timestamptz not null default now(),
  ended_at    timestamptz,
  git_commit  text not null,
  note        text
);

create table if not exists harness_sessions (
  run_id      uuid not null references harness_runs (id) on delete cascade,
  session_id  uuid not null,            -- learning_sessions.id (FK 없음: 정리 후에도 기록을 남긴다)
  scenario    text not null,            -- 'A1' | 'B2' | ...
  created_at  timestamptz not null default now(),
  primary key (run_id, session_id)
);
FK를 일부러 걸지 않는다

harness_sessions.session_id에 FK를 걸면 정리 시 cascade로 부기까지 함께 지워진다. "무엇을 지웠는지"의 기록이 정리에 의해 사라지는 것이 감사 관점에서 최악이라 참조 무결성을 포기한다. 앱 테이블이 아니라 하네스 테이블이므로 001 스키마 계약과 무관하다.

새 세션 id를 잡는 방법

WS가 연결 직후 보내는 session_started 프레임에 session_id가 실려 온다(api/ws.py). 러너는 이 값을 받는 즉시 harness_sessions에 적는다 — DB를 뒤져 "최근 세션"을 추정하면 캡틴이 같은 시각에 브라우저를 열었을 때 남의 세션을 지운다.

6콜백 배선

러너가 한 응답을 끝낼 때마다 orchestrator에게 통보가 오게 만드는 부분이다. 파일 3개로 끝난다.

6-1. 상태를 하네스 디렉터리에 격리한다

cd /Users/redstar/MyProject/OhMyEnglish
mkdir -p .harness/evidence
tmux display-message -p '#{session_name}:#{window_index}.#{pane_index}' > .harness/caller_pane.txt
printf '0' > .harness/count.txt
echo '.harness/' >> .git/info/exclude       # .gitignore를 고치지 않는다

통보 주소를 파일에 적어 두면 러너를 재기동하지 않고도 대상을 바꿀 수 있다. .gitignore가 아니라 .git/info/exclude를 쓰는 이유는, 하네스 배선이 앱 변경과 같은 diff에 섞이지 않게 하려는 것이다.

6-2. 통보 스크립트 .harness/notify.sh

#!/bin/bash
# Claude Code Stop 훅 → orchestrator 페인으로 완료 통보
P=$(cat)                                     # stdin = payload(JSON)
D="$(cd "$(dirname "$0")" && pwd)"
T=$(cat "$D/caller_pane.txt" 2>/dev/null); [ -z "$T" ] && exit 0

# 루프 차단 1차: 훅이 유발한 재실행이면 통보하지 않는다 (payload에 실측 존재)
python3 -c 'import json,sys; sys.exit(0 if json.load(sys.stdin).get("stop_hook_active") else 1)' \
  <<<"$P" && exit 0

# 루프 차단 2차: 왕복 상한
N=$(cat "$D/count.txt" 2>/dev/null || echo 0); N=$((N+1)); printf '%s' "$N" > "$D/count.txt"
[ "$N" -gt 120 ] && exit 0

R=$(python3 -c 'import json,sys
d=json.load(sys.stdin)
print((d.get("last_assistant_message") or "")[:400].replace("\n"," "))' <<<"$P")
TP=$(python3 -c 'import json,sys; print(json.load(sys.stdin).get("transcript_path",""))' <<<"$P")

6-4. 훅을 설정 파일로 물린다

Claude Code의 훅은 settings에 걸린다. 전역 ~/.claude/settings.json을 고치지 않는다 — 하네스 전용 파일을 만들고 --settings로 얹는다.

  window.__omy = { sent: 0, recv: { partial: 0, final: 0, audio: 0 }, played: 0 };
  // ② 클라이언트가 보낸 audio 프레임 계수
  const send = WebSocket.prototype.send;
  WebSocket.prototype.send = function (d) {
    try { if (JSON.parse(d).type === 'audio') window.__omy.sent++; } catch {}
    return send.call(this, d);
  };
  // ③ 수신 이벤트 계수 (앱은 socket.onmessage = ... 로 붙인다)
  const om = Object.getOwnPropertyDescriptor(WebSocket.prototype, 'onmessage');
  Object.defineProperty(WebSocket.prototype, 'onmessage', {
    get() { return om.get.call(this); },
    set(fn) { om.set.call(this, (ev) => {
      try { const m = JSON.parse(ev.data);
            if (m.type in window.__omy.recv) window.__omy.recv[m.type]++; } catch {}
      return fn(ev); }); }
  });
  // ④ 오디오 재생 시도 계수 (headless라 소리는 판정할 수 없다)
  const A = window.Audio;
  window.Audio = function (...a) { window.__omy.played++; return new A(...a); };
  return 'instrumented';
})()

공유 dev DB를 쓰기로 한 대가를 여기서 치른다. 순서를 바꾸면 복원이 부정확해진다.

10-0. 실행 전에 떠 두는 것 (P6과 함께)

create table if not exists harness_pattern_baseline as
  select id from error_patterns
   where user_id = '00000000-0000-0000-0000-000000000001';

하네스가 새로 만든 패턴만 골라내기 위한 기준선이다. 이게 없으면 "occurrence가 0인 패턴"을 지울 때 캡틴의 패턴을 함께 지울 위험을 배제할 수 없다.

10-1. DB 복원 — 3단계

-- ① 하네스 세션 삭제. cascade가 utterances → {error_occurrences, analysis_jobs}까지 지운다.
delete from learning_sessions
 where id in (select session_id from harness_sessions where run_id = :run_id);

-- ② frequency·last_seen_at 재계산 — 앱이 쓰는 식과 같다 (services/analysis.py).
--    앱이 count(*)와 max(u.created_at)으로 다시 세므로, 같은 식을 돌리면 원래 값이 복원된다.
update error_patterns p
   set frequency = agg.occurrences,
       last_seen_at = agg.last_seen_at
  from (select ep.id,
               count(eo.id)      as occurrences,
               max(u.created_at) as last_seen_at
          from error_patterns ep
          left join error_occurrences eo on eo.pattern_id = ep.id
          left join utterances       u  on u.id = eo.utterance_id
         where ep.user_id = '00000000-0000-0000-0000-000000000001'
         group by ep.id) agg
 where p.id = agg.id;

-- ③ 하네스가 새로 만들었고 이제 occurrence가 없는 패턴만 삭제.
delete from error_patterns p
 where p.user_id = '00000000-0000-0000-0000-000000000001'
   and p.id not in (select id from harness_pattern_baseline)
   and not exists (select 1 from error_occurrences eo where eo.pattern_id = p.id);
복원이 정확한 이유

frequency를 -2처럼 되돌리는 것이 아니라 앱과 같은 식으로 다시 센다. 앱 자체가 +1을 절대 하지 않고 항상 실제 행 수에서 재계산하기 때문에(analysis.py — "재시도마다 부풀어 오른다"는 주석이 그 이유다), 하네스 행을 지운 뒤 같은 식을 돌리면 하네스가 없었던 것과 같은 값이 된다. last_seen_at도 max(u.created_at)이므로 마찬가지다.

실패한 시나리오의 세션은 ①에서 제외한다 — 재현 근거를 지우지 않는다.

11제약과 함정

각 항목은 이 기계에서 확인한 사실이거나, 코드에서 직접 읽은 계약이다.

환경

  • :8000은 남의 앱이다. StockAgent 백엔드가 점유 중이고 /health에 version 키가 있다. 설계 문서와 HANDOFF.md의 실행 예시에 --port 8000이 남아 있으니 그대로 따르면 안 된다.
  • 프론트를 재기동하면 8000으로 떨어진다. app/frontend/.env.local이 없어서 lib/config.ts의 기본값이 쓰인다. 지금 떠 있는 서버는 .next/dev 청크에 localhost:8002가 인라인돼 있어 정상이다 — 즉 "지금 맞다"는 사실이 재기동 후에도 유지되지는 않는다.
  • 두 번째 프론트를 띄울 수 없다. main.py의 FRONTEND_ORIGIN이 http://localhost:3000 하드코딩이라 :3001 origin은 결과 조회 fetch가 CORS로 막힌다.
  • psql이 없다. podman exec ohmy-pg psql -U ohmy -d ohmyenglish를 쓴다.
  • 백엔드가 --reload 없이 떠 있다. 22시간 전에 뜬 프로세스는 그 시점의 코드다. ps -o lstart= -p <pid>가 마지막 소스 수정 시각보다 이전이면 낡은 코드를 테스트하는 것이므로 재기동하고 시작한다.
  • 백엔드를 죽인 직후 바로 띄우지 않는다. lifespan이 워커 종료를 최대 WORKER_SHUTDOWN_TIMEOUT = 15초 기다린다. /health가 응답하지 않는 것을 확인한 뒤 재기동한다.
  • 셸 작업 디렉터리가 이동한 채로 남는다. 검증 중 cd로 내려가면 이후 상대경로가 깨진다. cd <루트> && 형태나 절대경로로 쓴다.

앱의 테스트가능성 한계 (버그가 아니라 계약)

  • 스텁이 지연 0으로 재생한다. stub.py의 events()에 sleep이 없어 3턴이 밀리초 안에 끝난다. 결과: (a) 회색 partial의 픽셀 포착이 경합이고, (b) no_utterances를 앱 경로로 만들 수 없다 — 클라이언트가 즉시 end_session을 보내도 어댑터 펌프가 앞서 나가고, _relay가 DRAIN_TIMEOUT = 1초까지 스트림을 비워준다.
  • received_frames가 노출되지 않는다. 서버가 오디오 프레임을 받았다는 사실은 프로세스 안에서만 보인다 — 종단 증명이 두 조각으로 갈린다(C1).
  • 실제 발화 내용과 전사문은 무관하다. 스텁 모드에서 전사문은 픽스처가 결정한다 — 마이크에 무슨 소리를 넣어도 같은 3문장이 나온다. 버그가 아니다.
  • 공유 DB에서 절대값 단정은 실패한다. error_patterns는 unique (user_id, pattern_key)로 사용자에 붙는다. AC W-live의 frequency=2는 전용 스모크 DB 전제값이다 — 델타로 단정한다(A3).

러너 (Claude Code CLI)

  • 훅 payload 필드명이 kiro-cli와 다르다. 응답 본문은 assistant_response가 아니라 last_assistant_message다. 대신 stop_hook_active와 transcript_path가 있어 루프 차단과 이력 추적이 훨씬 쉽다(6-3 실측).
  • 전역 설정을 상속시킨다 — 의도적이다. superpowers-chrome 플러그인이 전역 enabledPlugins에 있어 --setting-sources project로 좁히면 use_browser를 잃는다. 대가로 전역 CLAUDE.md의 위임 지침도 함께 들어오므로 --disallowedTools Agent로 서브에이전트를 막는다.
  • 전역 Stop 훅이 이미 있다. 하네스 훅과 둘 다 발동할 것을 전제한다 — 첫 왕복에서 통보 중복 여부를 확인한다.
  • 여러 줄 프롬프트는 줄바꿈에서 조기 전송된다. 한 줄로 이어 보내거나, 서식이 중요하면 파일에 쓰고 경로로 지목한다.
  • send-keys에서 -t를 생략하면 자기 자신이 대상이 될 수 있다. 항상 명시한다.
  • capture-pane은 판정 근거가 아니다. TUI 덮어그리기로 서로 다른 프레임의 글자가 한 줄에 포개진다. 판정은 증거 파일과 transcript_path로 한다.
  • 도구 승인을 켜두면 첫 홉에서 멈춘다. 러너는 curl· podman·프로세스 기동을 수십 번 한다 — --permission-mode bypassPermissions로 띄운다.

브라우저

  • 기본 headless다. 소리를 귀로 판정할 수 없고, 자동재생 정책이 AudioContext를 suspend시킬 수 있다. 필요하면 show_browser로 전환하되 Chrome이 재시작되며 페이지가 GET으로 다시 로드된다 — 진행 중인 세션은 사라진다.
  • 마이크 합성은 미검증 기법이다. 플러그인에 --use-fake-*-for-media-stream 기동 플래그가 없어 페이지 안에서 합성해야 한다. C1의 첫 실행은 시나리오가 아니라 스파이크다.
  • 프로파일·포트가 동적이다. 기본 프로파일 superpowers-chrome, 포트 9222–12111. 다른 MCP가 먼저 잡으면 -2, -3으로 밀린다 — 포트를 고정값으로 가정하지 않는다(browser_mode로 확인).
