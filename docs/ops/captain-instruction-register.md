# 캡틴 지시 대장 — 지시 → 태스크 매핑

> **이 문서는 상태를 담지 않는다.** 지시가 **어느 태스크로 갔는지**만 담는다.
> 상태의 정본은 **Backlog.md**다 — `backlog task list`로 읽는다. 두 곳에 상태를 쓰면 한쪽이 낡는다.
>
> **왜 생겼나 (2026-09-06)**: 캡틴이 프론트엔드 테스트 에이전트를 **두 번 물었고 두 번 다 답만 하고
> 만들지 않았다.** 태스크(`TASK-17`)는 등록돼 있었으나 **원장을 보고 다음 행동을 고르지 않았기 때문에**
> 누락됐다. 원장이 있는 것과 원장이 행동을 정하는 것은 다르다.
>
> **누가 챙기는가**: 팀리드(이 세션)다. 도구가 아니라 사람이 소유한다 — 아래 §3의 강제 장치가
> 그것을 잊지 못하게 한다.

---

## §1. 무엇이 어긋났나 — 재발 방지의 근거

| 시각 | 무슨 일 |
|---|---|
| 캡틴 회신 항목 2 | *"새로 만든 프론트엔드 테스트 Agent를 **활용하여 착수**(존재여부 먼저 판단)"* |
| 등록 | 존재하지 않음을 확인하고 `TASK-17` 등록. **선행 조건을 `TASK-18`(절차 문서)로 걸었다** |
| 10:21 | `TASK-18` 완료 → **`TASK-17`이 착수 가능해졌다** |
| 10:28 | ⚠️ **팀리드가 그 관측을 직접 해버렸다.** 에이전트를 쓰지 않았다 |
| 캡틴 1차 질문 | *"frontend test agent 질문은 없는데, 이미 task에 기록되어 개발할 계획인가?"* → **답만 했다** |
| 캡틴 2차 질문 | *"frontend test agent는 개발이 되었나?"* → **그때 만들기 시작했다** |

**근본 원인 둘 — 지연이 아니라 두 가지 다른 실패다.**

1. **다음 행동을 원장에서 고르지 않았다.** 대화 흐름으로 골랐다. 원장은 기록용이었고 **구동용이
   아니었다.**
2. ⚠️ **더 나쁜 쪽**: 캡틴 지시가 *"에이전트를 활용하여 착수"*였는데 **팀리드가 그 일을 손으로
   해버렸다.** 결과물(관측)은 나왔지만 **지시받은 방식이 아니었고**, 그래서 에이전트가 불필요해
   보이게 됐다. **산출물이 나왔다고 지시가 이행된 것이 아니다.**

**제약 3개**:

**대체 검증**: 설계 오류는 **구현 태스크의 red→green 이 잡는다** — 설계서를 다시 읽어 잡는 것보다 싸고
확실하다. 대신 **설계서 자체의 문장 정합(개수·방향·시그니처 서술)은 검증 없이 남는다** — 이것이 이
결정이 받아들인 비용이고, 그래서 각 구현 태스크 AC 에 *"정본은 설계서 §N"* 을 명시해 구현자가 본문을
보게 했다.

**결정 21 — 평문 비밀번호는 회전하고 문서에서 제거한다.** `docs/ops/shared-database-naming-rules.md`

**기각한 대안 2개와 근거**:
- **git 이력 재작성** — remote·클론이 없어 지금이 가장 싸지만 **모든 커밋 해시가 바뀐다.** 이 리포는
  handoff·원장·설계서·`pitfalls.md`·캡틴 결정 기록에 **해시를 수십 건 적어 둔 문서 밀도가 비정상적으로

  ⚠️ **회전하면 이력의 값이 무용지물이 되므로 이 대안의 이득이 대부분 사라진다.**
- **무기한 비공개** — 가장 싸지만 **비밀번호가 유효한 채로 이력에 남아** 공개 전환·리포 인계 때 같은

**제약**:
1. ⛔ **공유 DB 다** — 그 역할은 En-Coach 가 쓴다. 회전은 **상대 서비스 설정도 함께 고쳐야** 하고,
   작업세션은 **남의 리포 설정을 직접 고치지 않는다.** 절차와 En-Coach 쪽에서 바꿔야 할 것을 정리해 올린다.
2. ⛔ **`ALTER ROLE` 은 공유 자원 변경이므로 캡틴 확인 후에 실행한다.** 인스턴스 단위 조작
   (재시작 · `ALTER SYSTEM` · `ALTER DATABASE … SET TimeZone`)은 하지 않는다.
3. **문서에서 값을 제거하고 「어디서 얻는가」로 바꾼다** — 전달이 목적이었으므로 대체 경로가 필요하다.
4. ⚠️ **`TASK-23`(원격 연결 + 첫 푸시)은 이것이 닫히기 전까지 착수하지 않는다.**
5. **`TASK-38`(AWS access key 로테이션 — 대화 기록 경유 노출)도 같은 종류의 미결이다.** 함께 보라 —
   그것 역시 살아 있는 자격증명이고 실행은 캡틴 몫이다.

**결정 19 — `build_system_prompt`는 조립 재료 4개 + 드릴 설정값 2개(keyword-only) = 6인자다.**

더 나쁘게 코드 주석 2곳(`app/backend/app/audio_gateway/nova.py` · `app/backend/app/services/sessions.py`)이

critic 재검증 2회차가 **R-2(HIGH)** 로 찾았다.
**승인 근거**(캡틴이 이 판단을 받아들였다): 결정 15가 센 「4개」는 **조립 재료**(놓친 소리·계획·질문·무대)이고

**과소 계수 경로 하나를 새로 찾았다**(학습자 선발화가 세어지지 않는다) — 문턱이 가능해도 거짓 미달이
쌓일 수 있으므로 미달 로그를 지시문 수정 근거로 쓰기 전에 이 결정을 다시 읽는다.
⚠️ **상한 20을 낮추자는 제안이 아니다** — 이 실측은 낮출 근거를 만들지 않았고, AC#2가 준비했던
선택지 셋(`drill_turns_min` 하향 · 기대값 상한 · 세션 길이 재정의)은 **올릴 필요가 없어졌다.**

**결정 18 — 결과 API 의 `drill` 키와 결과 화면의 한 줄, 둘 다 승인.** 설계서
`docs/design/2026-09-07-scenario-and-drill-turns-design.md` 머리말 표의 **항목 4**(결과 API 응답에
`drill` 키 — `corrections`와 같은 R2 상태 규약)와 **항목 5**(결과 화면에 사실 진술 한 줄이 는다)다.
**왜 이 기록이 필요했나**: 그 표가 *"캡틴이 전부 승인했다"* 고 적었지만 **항목 1·2·3은 결정 15,
항목 6은 결정 16으로 정본이 있는데 4·5는 어느 정본에도 없었다** — critic 재검증이 지적하고 작업세션이
확인했다(B-6). 그 표의 「✅ 승인」을 근거로 쓰면 **자기 참조**이고, 결정 12가 **「공개 계약」과
「화면에 보이는 것」**을 올릴 항목으로 명시했으므로 근거가 리포 안에 있어야 한다.
⚠️ **작업세션은 리포 밖의 구두 승인 여부를 확인할 방법이 없어 미결로 남기고 캡틴에게 물었다** —
그것이 옳은 처리다. 답이 「승인」이었으므로 이 줄이 그 근거가 된다.
**제약은 설계서가 이미 소유한다**(여기서 재서술하지 않는다): R2 상태 3개(`analyzing`·
`connection_failed`·`no_utterances`)에서 **키와 로그를 함께** 뺀다(4판이 로그를 더했다 — critic B-4) ·
⛔ **화면에 두 수를 내보내지 않는다**(`9 / 12`가 가장 점수처럼 보인다) · **미달일 때만 한 문장** ·
**주어를 세션에 두고 학습자를 주어로 쓰지 않는다**(결정 10: *"미달의 주어는 학습자가 아니라 대화 모델"*) ·
낱말 선택만 톤 계약의 몫이다.
⚠️ **일반화**: 설계서 머리말의 승인 표는 **정본이 아니라 색인**이다. 승인 항목이 늘면
**이 파일에 줄을 함께 추가한다** — 안 하면 다음 세션이 같은 구멍을 다시 발견한다.

**결정 17 — `drill_count` 기본값은 5다.** `app/config.py`의 `drill_count`를 `3` → **`5`**로 올린다
(`ge=1` 하한은 그대로 · **상한은 여전히 발명하지 않는다**). `/.env.example`의 `DRILL_COUNT`도 같이 5.
**무엇이 틀렸었나**: 설계서 §2.2가 지시문에 `questions[:drill_count]`만 열거하게 했고 기본값이 3이었다 —
그러면 **질문 4~5개인 계획의 질문이 대화에 도달하지 않는다.** 그런데 **결정 2**(`docs/design/2026-09-06-captain-decisions.md:17`)는
*"계획이 만든 질문 **3~5개**를 대화 상대에게 전달할까 → **전달한다**"*이고 **결정 9**(`:139`)도
*"계획 = 목표(초점 패턴과 **질문 3~5개**)"*다. **작업세션이 그 두 줄을 직접 열어 확인했다.**
⚠️ **기본값 `3`은 캡틴이 정한 값이 아니라 이전 세션의 유도였다**(설계서 §3 표) — 그래서 이 정정은
캡틴 결정을 뒤집는 것이 아니라 **유도가 덮고 있던 결정 2를 복원하는 것**이다.
**왜 5인가**: `session_plans.questions`의 DB CHECK가 `3 ≤ len ≤ 5`(`007:42-43`)이므로 **5면 절단이
원리적으로 일어나지 않는다.**
⚠️ **H-5는 그대로 닫혀 있다** — 운영자가 `drill_count`를 낮추면 **열거와 기대값이 함께** 줄어들므로
설정값이 여전히 대화를 바꾼다. 「통과 문턱만 바꾸는 노브」로 되돌아가지 않는다.
**제약**: ① 그 필드의 **근거 주석을 같은 커밋에서 고친다**(지금은 결정 1만 근거로 든다 → 결정 2·17을
함께 적는다) ② `tests/unit/test_config.py`의 기본값 단정을 5로 고친다(**회귀 수정이고 T0 red가 아니다**)
③ **H-5 tripwire는 유지한다** — 「질문 5개·`drill_count=3`이면 3개만 열거된다」를 값을 **명시 주입**해
계속 단정한다 ④ **새 tripwire 1건**: 기본값에서 질문 5개가 **전부** 열거된다(= 결정 2 회귀 방어).
**발견 경로**: critic 재검증(`CHALLENGE`)의 HIGH 1건. **결정 12가 「기존 캡틴 결정과의 충돌」을 올릴
항목으로 명시했고 이전 판이 올리지 않았다** — 2판 유도 2와 같은 형태다(그때는 승인 게이트 회피였고
이번엔 언급조차 없었다).

**결정 15 — `build_system_prompt`는 인자 4개다.** `(known_sounds, plan, questions, scenario)` ·
`create_voice_adapter(settings, *, known_sounds, plan, questions, scenario)` ·
`_load_prepared_plan_or_none`의 반환을 **`PreparedPlan | None`**으로 올린다.
⚠️ **이것은 이전에 승인한 「인자 3개」의 정정이다.** 근거(감독 세션이 직접 확인): `api/ws.py:135`가
`return prepared.instruction if prepared is not None else None`으로 **`PreparedPlan`을 버리므로**
인자가 3개면 `questions`가 갈 길이 없다. 기각한 두 길과 그 이유는 설계서가 소유한다 — 특히
`SessionInstruction`에 넣는 길은 `services/sessions.py:143-148`이 이름 붙인 실패 모드(필수 필드가
늘면 **저장된 모든 행**이 한꺼번에 검증 실패)를 그대로 밟는다.

**결정 16 — 기대값은 마이그레이션 009의 새 컬럼에.** `learning_sessions.drill_turns_expected integer`
(nullable · `check (> 0)`). null = 계획 없이 시작한 세션 = 관측 대상 아님.
⚠️ **`summary` jsonb를 쓰지 않는다** — 그 컬럼에는 **문서화된 다음 소유자가 있다**: `docs/database-schema.md`
*"`summary`(세션 총평)는 `summarize_session`과 함께 다음 슬라이스에서 채워진다"*이고

확인). "앱 참조 0곳"은 코드엔 참이지만 결론으로 틀렸다.
**제약**: **008은 `TASK-26` 예약**이므로 009 · 적용 전 `pg_dump -n public` 백업 → 적용 → **기존 행 수가

않는다**(그 컬럼은 여전히 총평의 것이다).
**착수 가능 확인(감독 세션 직접 조회)**: 마이그레이션은 `001·003~007`뿐이라 **009가 비어 있다** ·

**결정 13 — 미수신 리뷰 상한.** 위임한 리뷰·판정이 오지 않으면 **1회 재발송**한다. 그래도 오지 않으면

멈추는 것은 승격이고 진행이 아니다. 근거: 이 리포에 *"위임한 리뷰는 안 돌아올 수 있다"*가 실측된 함정으로
있고, 잊힐 수 있는 메시지 하나에 진행 전체를 묶는 비용이 더 크다.

**역할 분리** — 어긴 사례가 이미 있다(2026-09-07 감독 세션이 설계 방향 2건을 유도했고 즉시 철회했다):

| 주체 | 하는 일 | ⛔ 하지 않는 일 |
|---|---|---|
| **감독·전달 세션** | ① 캡틴에게 묻고 답을 전달 ② **캡틴 결정 기록** ③ 원장 상태·AC 갱신 ④ **게이트를 직접 돌려 실측값 확보** ⑤ 진행 확인 | **설계서·개발코드를 쓰지 않는다. 설계 판단을 하지 않는다** — 무엇을·어디를 고칠지, 계약을 어떻게 넓힐지, 마이그레이션 필요 여부, 자료구조 모양, 지시문 문장은 **전부 작업세션 것**이다. 읽는 것은 무해하고 확인은 감독의 몫이다 |
| **작업세션** | 설계서 작성과 **그 안의 모든 결정** · 구현 · TDD · 테스트 | 캡틴 결정 1~12을 재론하지 않는다 |

**결정 12의 판별 기준 — 되돌리기 어려운가로 가른다.** 캡틴에게 **올린다**: 스키마·마이그레이션 · 공개
계약(함수 시그니처·WS 이벤트·결과 API 응답 모양) · 요구사항 판정 · **기존 캡틴 결정과의 충돌** · 화면에
보이는 것. **올리지 않는다**: 되돌리기 쉬운 판단 — 대신 `…-captain-decisions.md` §3 선례대로
**「내가 유도한 것」 절에 모아** 표시한다(*"틀렸으면 이 줄만 뒤집으면 된다"*).

⛔ **캡틴이 해제한 것은 「캡틴 승인」 하나뿐이다.** 품질 게이트(TDD·SVG·리뷰·게이트 수치·원장 리듬)는
그대로이고 **정본은 `~/.claude/rules/`와 `handoff/HANDOFF.md`다 — 여기서 재서술하지 않는다.**

## §3. 강제 장치 — 잊지 못하게 하는 방법

### ① 다음 행동을 **원장에서** 고른다

작업을 시작할 때 **먼저 원장을 조회하고 태스크 ID를 말한 뒤** 착수한다.

```bash
backlog task list -s "In Progress"          # 이미 손댄 것부터
backlog task list -s "To Do" --priority high # 캡틴이 강조한 것
```

⚠️ **태스크가 없는 일을 하고 있다면 그것을 먼저 등록한다.** 등록 없이 한 일은 다음 세션에
전달되지 않고, 캡틴에게도 보이지 않는다.

### ② 캡틴 지시에는 **라벨과 우선순위**를 건다

- 라벨 **`caps-req`** — 캡틴이 직접 요청한 태스크. 현재 **22건**.
- **`--priority high`** — 캡틴이 **두 번 이상 언급**했거나 다른 작업을 막고 있는 것.

```bash
backlog task list -s "To Do" | grep -c .    # 남은 개수
backlog task edit TASK-N --priority high --label caps-req
```

### ③ 매 보고 끝에 **미이행 지시**를 노출한다

보고를 마칠 때 `caps-req` 중 `To Do`·`In Progress`인 것을 **개수와 함께** 적는다.
⚠️ **"진행 중"이라고만 쓰지 않는다** — 어느 태스크 ID인지 적는다. ID가 없으면 추적이 안 된다.

### ④ "방식"이 지시된 경우 **산출물로 대체하지 않는다**

지시가 *"X를 활용해서 해라"*면 **X를 만들어 쓰는 것까지가 이행**이다. 손으로 해서 결과를 내면
**그 지시는 미이행이다.** 결과가 나왔다고 표시하지 않는다.

### ⑤ 순서를 바꿀 때는 **그 사실을 말한다**

선행 조건을 걸어 캡틴 지시를 뒤로 미루면 **왜 미루는지와 언제 하는지를 그 자리에서 말한다.**
`TASK-17`을 `TASK-18` 뒤로 돌린 것 자체는 근거가 있었다(절차 정본이 있어야 가리킬 수 있다) —
**잘못은 미룬 것이 아니라 미룬 뒤 그것을 잊은 것이다.**
