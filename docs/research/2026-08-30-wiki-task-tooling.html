결론

A. 위키 → Otter Wiki1순위

git 리포 자체가 저장 계층이라, 네가 원한 "정본 = 리포 평문 md, 버전 이력 = git 커밋"이 우회 없이 성립한다. 페이지 목록도 DB 인덱스가 아니라 디스크를 os.walk로 훑는다. 서비스 1개·SQLite·외부 DB 0, MIT, v2.24.0(2026-08-29)로 매우 활발.

SQLite에는 사용자·환경설정·초안·렌더캐시만 들어가고 페이지 본문·버전 이력 테이블이 아예 없다 — 도구를 버려도 문서는 평문 md로 남는다(탈출 비용 0).

B. Plan/Task/PR → Gitea 네이티브1순위

이슈·PR 리뷰 UI·칸반(Projects)·위키를 단일 프로세스 하나로 덮는다. 공식 darwin-arm64 바이너리와 Homebrew 병(arm64_tahoe)이 있어 컨테이너·리눅스 VM·외부 DB가 모두 0이다. MIT, v1.27.3(2026-08-29).

지금 이 리포는 remote가 없어 PR 개념 자체가 없는데, 로컬 forge를 remote로 붙이면 그게 한 번에 해결된다. 유휴 165MB는 내가 직접 확인한 값.

왜 이렇게 갈렸나 — 판정축

리소스를 1순위 축으로 두자 "컨테이너냐 네이티브냐"가 결론을 지배했다. 이 맥에서 podman machine 게스트는 컨테이너 0개 상태에서 이미 ~450MB를 커밋한다(podman machine ssh 'free -m' 실측: 컨테이너 기동 전 used 454MB / total 3890MB). 즉 컨테이너 경로를 택하면 앱이 100MB든 상관없이 네가 정한 예산(유휴 ≤512MB 적합)의 대부분을 VM이 먼저 먹는다.

주의: macOS Virtualization.framework 회계 특성상 호스트 ps로는 vfkit 17MB + gvproxy 30MB로 작게 보인다. 어느 쪽을 "리소스"로 셀지에 따라 컨테이너의 불이익 크기가 달라진다 — 이 보고서는 게스트 free -m 기준으로 셌다.

그리고 탈락은 대부분 리소스가 아니라 "정본 위치" 때문이었다. 무거워서 떨어진 건 GitLab·Plane 둘뿐이고, 나머지는 기존 마크다운을 제자리에서 정본으로 두지 못해서 떨어졌다.

A. 위키 — 후보별 판정

Otter Wiki 채택 시 반드시 처리할 함정 3건 중요

  1. 대문자 파일명이 안 보인다. RETAIN_PAGE_NAME_CASE=False가 기본이라 경로를 .lower() 한다(server.py:52). 위에서 확인했듯 이 리포엔 TASKS.md·HANDOFF.md·PRD.md가 있다 → RETAIN_PAGE_NAME_CASE=True를 반드시 켜라. 메인테이너가 issue #160에서 같은 답을 했다.
  2. 원격 push/pull은 공식적으로 experimental. 병합 충돌 해결 UI가 없고 reset_to_remote는 fetch 후 hard reset이다. 로컬 리포를 직접 가리키는 용도로만 쓰고 원격 동기화에 의존하지 말 것.
  3. 저장 안 한 초안·렌더 캐시는 SQLite에 갇힌다. 커밋된 문서는 안전하지만 편집 중 초안은 md가 아니다.

추가 주의: 앱 리포 루트에 직접 붙이면 위키 편집이 작업 브랜치에 커밋을 만든다. 별도 clone이나 docs 전용 브랜치를 REPOSITORY로 두는 편이 안전하다 (이 부분은 미검증).

대안 — SilverBullet A 2순위

폴더가 정본이고 서버에 DB가 아예 없다(인덱스는 캐시라 언제든 재생성). ADR-003이 "Markdown is the source of truth... the index is a cache, not the canonical store"라고 명시하고, "별도 저작 DB(Notion/Confluence 방식)는 Rejected"라고 못 박았다. 위키링크·백링크·전문검색이 1급 기능이라 '위키다움'은 Otter Wiki보다 강하다. Developer ID 서명된 39MB 단일 바이너리, MIT.

결정적 macOS 제약: 공식 Install 문서가 대소문자 구분 없는 기본 APFS에서의 구동을 "highly discouraged"로 명시하고 case-sensitive APFS 볼륨을 따로 만들라고 한다. 유휴 RSS 실측값은 이번 조사에서 확보하지 못했다(공식 수치는 self-report "few hundred MB"뿐).

탈락 — 이유가 리소스가 아니다

LeafWiki — 리소스는 가장 가볍다(네이티브 유휴 36.6MB 실측). 하지만 앱 밖에서 넣은 .md에 leafwiki_id를 포함한 관리 frontmatter 블록 전체를 디스크 파일에 되쓰기하고 opt-out 옵션이 없다. README가 직접 인정한다: "that ID write-back will show up as an extra diff you didn't make yourself." → "기존 md를 수정 없이 읽는 도구"가 아니고 git diff를 오염시킨다.

Wiki.js — 정본이 DB이고 git은 동기화 타깃이다. 공식 문서 축자: "A Git repository must be dedicated to Wiki.js. It is not possible to use only a subfolder or submodules at the moment." → 이 리포의 docs/·handoff/를 대상으로 지정하는 것이 공식적으로 불가능하다. 기존 콘텐츠는 관리자 화면에서 Import Everything을 수동 실행해야 하고, 모듈 비활성 구간에 생긴 콘텐츠는 Add Untracked Changes+Force Sync를 손으로 돌려야 복구된다. AGPL-3.0, v2.5.314(2026-05-01)로 상대적으로 느리고 v3는 2023년 이후 미출시.

Outline — 라이선스가 Business Source License 1.1이고, 라이선스 본문이 스스로 "is not an Open Source license"라고 명시한다 → 오픈소스 요건에서 탈락. Docmost — 메인테이너가 "Postgres is the only supported database"라고 공식 답변(설계 결정이지 백로그가 아님).

B. Plan/Task/Status/PR — 후보별 판정

대안 — Forgejo B 2순위

SQLite가 문서상 기본이자 저활동 인스턴스에 공식 권장이고, 배포 바이너리에 SQLite가 내장돼 외부 DB 준비 단계가 아예 없다(설치 문서의 섹션 제목이 문자 그대로 "Optional: Set up database"). GPL-3.0-or-later, v16.0.3(2026-08-20).

이 맥에서 Gitea보다 불리한 단 하나의 이유: 공식 릴리스 자산이 리눅스 전용(amd64/arm-6/arm64)이고 darwin 바이너리가 없다(Codeberg 릴리스 API 실측). Homebrew 병으로 네이티브 설치하거나 podman VM ~450MB를 감수해야 한다. 또 공식 문서에 하드웨어/RAM 요구사항이 전혀 없다(docs 리포 md 138개 전수 grep → 유효 히트 0건).

상주 0 후보 — 확인은 됐지만 검증은 안 된 유력주 미검증

Backlog.md는 정본이 리포 안 평문 마크다운이고 서버·DB가 아예 없다 — TASKS.md 308줄을 "태스크 1개 = md 1파일"로 쪼개 그대로 옮길 수 있어 네 제약과 가장 잘 맞는 부류다. 다만 이 후보는 3표 적대적 검증 단계에 오르지 못했다(예산이 상위 25개 주장에서 소진). 채택 검토 시 별도 확인이 필요하다.

git-bug은 이슈를 작업트리 파일이 아니라 git 오브젝트 자체로 임베드한다 → "리포에 데이터가 남는다"는 맞지만 "정본은 md 파일"이라는 네 조건은 충족하지 못한다(도구를 버리면 평문 md가 아니라 커스텀 git ref만 남는다).

리소스 과잉으로 탈락

GitLab CE — "PostgreSQL is the only supported database"(SQLite 불가) + Redis/Valkey 별도 요구. 공식 requirements가 메모리 제약 환경의 하한조차 "at least 8 GB of memory"로 명시하고 "Disable swap where possible"까지 적는다. 배포 단위는 1컨테이너지만 그 안에 Postgres·Redis·Gitaly·Puma·Sidekiq·Nginx 등 6+ 서비스가 상주한다.

Plane — compose 최상위 서비스 13개(web/admin/space/api/worker/beat-worker/migrator/live/postgres/valkey/rabbitmq/minio/proxy). SQLite로 축소가 구조적으로 불가능하다 — settings/common.py가 ENGINE을 postgresql로 하드코딩하고 마이그레이션이 django.contrib.postgres.ArrayField를, 검색이 ArrayAgg를 쓴다(둘 다 PostgreSQL 전용) → SQLite에서는 migrate 자체가 실패. 워커 OOM 이슈 #6671이 여전히 open. AGPL-3.0, v1.4.2(2026-08-23)로 유지보수는 활발하나 1인용으로는 과잉.

"유휴 메모리"는 빈 인스턴스 하한이다. 리포·이슈가 쌓이고 Gitea의 bleve 인덱서가 돌면 오른다. Plane 4GB·GitLab 8GB는 호스트 프로비저닝 요구사항이지 유휴 실측값이 아니므로 같은 칸에서 직접 비교하지 말 것. 컨테이너 경로는 여기에 podman VM ~450MB를 더해야 한다.

통합안 vs 분리안

통합 — Gitea 하나

~165MB · 프로세스 1개

이슈+PR 리뷰+칸반+위키를 한 몸으로. 리소스 총량으로는 명백히 우월하고, Gitea는 리포 브라우저에서 docs/**.md를 그대로 렌더링하니 "읽기 전용 문서 뷰 + 이슈/PR"이면 이것만으로 충분하다.

한계: forge의 Wiki 기능은 별도 <repo>.wiki.git을 정본으로 쓰므로 "리포 docs/가 위키의 정본"이라는 요건을 만족하지 못한다. 이 성질은 이번 라운드에서 실행 검증하지 않았다 — 채택 전 로컬 Gitea에서 1회 확인 권장.

분리 — Otter Wiki + Gitea

~270~330MB · 프로세스 2개

위키를 따로 두는 비용은 네이티브 기준 약 +160MB, 컨테이너 기준 약 +550MB(VM 포함). 이 값을 내는 이유는 단 하나 — 리포 docs/ 마크다운을 위키의 정본으로 쓸 수 있다는 것.

추천 판단: 위키링크·백링크·전문검색 기반 지식 그래프가 실제로 필요해질 때까지는 통합안으로 시작하고, 필요해지면 같은 리포에 Otter Wiki를 얹어라.

첫 걸음

  1. brew install gitea → SQLite로 기동 → 이 로컬 forge를 git remote add local로 붙이고 push. 이슈·PR·칸반이 한 번에 생긴다. 최소 app.ini(DB_TYPE=sqlite3, INSTALL_LOCK=true, SECRET_KEY, HTTP_ADDR=127.0.0.1)만으로 설치 위저드 없이 HTTP 200이 뜨는 것을 확인했다 — 실측에 쓴 파일은 /tmp/giteatest/custom/conf/app.ini에 남아 있다.
  2. TASKS.md 308줄을 즉시 폐기하지 말고 원장으로 유지한 채, 진행 중 태스크만 이슈로 이중 등록해 2주 병행 운영한 뒤 정본을 하나로 접어라. 이 리포의 규약이 "TASKS.md = 상태의 정본"이라, 정본을 한 번에 옮기면 세션 인계 지표가 깨진다.
  3. 위키가 필요해지면 Otter Wiki를 REPOSITORY=<리포 경로> + RETAIN_PAGE_NAME_CASE=True로 얹어라. 대문자 파일 3개가 실재하므로 두 번째 옵션은 선택이 아니라 필수다. 백업 디렉터리(docs/backup/**, handoff/backup/**)를 위키에 노출하지 않는 공식 수단은 확인되지 않았다 — 별도 clone이나 docs 전용 브랜치를 대상으로 두는 우회가 필요할 수 있다.

한계 — 이 보고서가 답하지 못한 것

검증되지 않은 후보: 네가 목록에 넣은 것 중 DokuWiki·Gollum·TiddlyWiki·Trilium·MkDocs·mdBook·Quartz 등 정적 생성기·Obsidian·Logseq·Joplin, 그리고 B의 Vikunja·Kanboard·Wekan·Leantime·Taskwarrior·dstask·radicle·jj는 3표 검증 단계에 오르지 못했다(상위 25개 주장에서 예산 소진). 참고로 Vikunja는 Homebrew formula가 없다(API 404).

1차 수집 단계 근거만 있는 것 (3표 검증 미통과 — 참고 신호로만): Focalboard는 README 최상단에 "This repository is currently not maintained"가 있고 리포가 mattermost→mattermost-community로 이관됐으며 최근 52주 커밋이 0건이다. 단 GitHub archived 플래그는 여전히 false라 자동 필터로는 걸러지지 않는다. Dendron은 README에 "maintenace only, active development has ceased"가 메인테이너 선언으로 있다. git-appraise는 archived=false이지만 master 마지막 커밋이 2023-08-12로 약 3년 무활동이다(updated_at 2026-08-22는 star 등 메타데이터 시각이라 코드 활동 지표가 아니다).

기각된 주장 6건 — 근거로 재인용하지 말 것: GitLab "16GB/8vCPU 기준선"(0-3), Wiki.js "bi-directional은 기본 5분 스케줄 미러"(0-3), LeafWiki "git 백업은 단방향 push"(0-3, 방향성은 여전히 쟁점이나 탈락 사유인 frontmatter 되쓰기는 이와 독립적으로 3-0 확정), Forgejo "바이너리 복사+chmod로 끝나는 단일 프로세스 배포"(0-3), Plane "podman에서 안 뜬다"(1-2), GitLab "8GB 하한이라 조건부 등급에도 못 든다"(1-2).

시효: Gitea v1.27.3·Otter Wiki v2.24.0·SilverBullet push가 전부 2026-08-29, Forgejo v16.0.3이 2026-08-20 — 조사 시점 열흘 내라 버전·수치는 수 주 안에 낡는다.

  • SilverBullet의 네이티브 유휴 RSS는 얼마이고, 대소문자 구분 없는 기본 APFS에서 실제로 어떤 오류가 나는가(공식 문서는 "highly discouraged"라고만 하고 실패 양상을 적지 않는다).
  • Otter Wiki에서 백업 디렉터리와 소스 코드를 위키 노출에서 제외하는 공식 수단이 있는가 — 없으면 별도 clone이 필수인데, 그러면 "리포 md가 제자리에서 정본"이라는 성질이 약해진다.
  • 상주 0 대안(Backlog.md·dstask 등)이 TASKS.md 308줄을 대체할 수 있는가 — 확인되면 리소스 0으로 B의 상당 부분을 덮는다.
