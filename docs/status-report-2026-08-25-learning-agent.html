07 · ROLE SPLIT

역할 분담 — 승인된 경계

캡틴 질문이 출발점이었다: "LLM 에이전트만으로 충분히 학습 패턴을 파악하고 문제를 제시할 수 있지 않나." 대부분 맞다. 규모가 작아서 더 그렇다 — 하루 3발화면 1년 뒤에도 발화 1,000건 수준이라 한 사람의 전체 이력이 컨텍스트에 들어간다.

담당하는 일왜
Claude (판단·생성) 무엇이 약점의 본질인지, 어떤 질문·상황으로 연습시킬지, 난이도, 지시문 작성 점수식으로 산출 불가능. "긴 문장을 시도할 때만 시제가 무너진다" 같은 통찰은 frequency=7을 아무리 봐도 안 나온다
쿼리 (장부) 오늘 복습 대상 목록, 만성 지표 숫자, 최근 창 추출, 복습 단계 전이 놓침이 조용히 일어나면 안 된다. LLM에게 "떠올려라"라고 하면 어떤 패턴은 언급되지 않고 잊히는데, 사용자도 개발자도 알아챌 방법이 없다. 회귀 테스트도 여기서만 가능하다
Nova (응대) 실시간 대화 Claude를 음성 턴 동기 경로에 넣지 않는다 (PRD.md:112)
핵심 논거: LLM 단독안에서도 커버리지를 확보하려면 "기억해서 떠올려라" 대신 "이 목록을 받아서 판단하라"로 줘야 한다. 그게 되는 순간 이미 하이브리드다. 즉 장부를 없앨 수는 없고, 그것이 쿼리인지 희망인지만 고를 수 있다. 이 프로젝트는 Phase 1에서 이미 같은 선택을 했다 — 분석 워커는 "어떤 발화를 분석할까"를 Claude에게 묻지 않고 analysis_jobs 클레임 쿼리가 정한다.

임계값을 발명하지 않는다

"재발 며칠 이상이면 만성인가" 같은 판정을 설계가 숫자로 정하지 않는다. 쿼리는 사실만 제공하고 Claude가 판단한다. 예외는 이미 문서로 확정된 값뿐이다 — 복습 1·3·7일, 재시도 상한 5, 초점 패턴 1~2개, 질문 3~5개.

08 · TIMING

언제 도는가 — 그리고 왜 느려지지 않는가

캡틴 질문: "Claude가 만들고 Nova가 대답하면 느리지 않은가." 계획을 세션 시작이 아니라 앞선 세션이 끝날 때 만들기 때문에 느려지지 않는다.

세션 종료 (ended_at + status 기록) └─ 같은 트랜잭션에서 analysis_jobs 에 job 등록 (job_type='plan_next_session') └─ 워커가 claim → Claude 1회 호출 └─ session_plans + learner_notes + current_level 갱신을 한 트랜잭션으로 커밋 다음 세션 시작 └─ 준비된 session_plans 1행을 읽어 즉시 시작 └─ 없으면 learning_scenarios 폴백 (학습이 막히지 않는다)

지연 예산 — 사용자가 기다리는 경로에 Claude 호출이 0개

경로Claude 호출체감
세션 시작✓ 없음session_plans 1행 조회 + 지시문 전달 — DB 조회 1회
세션 중 대화✓ 없음Nova 단독. Nova 자체 지연만
턴마다 분석있음 (비동기 job)0 — 음성 응답 경로 밖 (Phase 1과 동일)
계획 생성있음0 — 직전 세션 종료 시 미리 실행

결론: 추가 아키텍처가 필요하지 않다. Phase 1이 분석을 음성 경로에서 떼낸 것과 같은 구조다.

⏸ 남는 틈 1건 — 지연이 아니라 기능 퇴화다 (이후 과제, 캡틴 결정)

세션을 끝내고 곧바로 다시 시작하면(예: "추가 학습" 연속 실행) 계획 생성이 아직 끝나지 않아 폴백으로 시작된다. 느려지는 것이 아니라 패턴 기반 선택이 조용히 꺼진다.

보완책 후보 2개 — 둘 다 새 인프라가 필요 없다: ① 새 계획이 없으면 폴백 대신 직전 계획의 남은 질문을 이어 쓴다, ② job 등록을 세션 종료가 아니라 마지막 발화의 분석 완료 시점으로 앞당긴다.

지금 반영한 조치: 지시문 가변부에 크기 상한을 둔다 (길면 Nova 세션 초기화가 느려질 수 있음). 구체 수치는 Phase 2에서 실측해 정한다 — 지금 발명하지 않는다.

계획이 없을 때 — 학습이 막히지 않는다

첫 세션 · 계획 생성 실패(attempts 5회 소진) · 스키마 검증 거부 — 세 경우 모두 learning_scenarios에서 수준에 맞는 행을 골라 시작한다. 계획 부재는 session_plans 행이 없는 것으로 판별한다.

09 · INPUT

Agent가 받는 입력 — 3계층

전체 이력을 매번 넣지 않는다. 컨텍스트에는 들어가지만 비용과 지연을 의미 없이 늘린다.

① 오늘 다뤄야 하는 목록

next_review_at <= clock_timestamp()인 패턴 전부. 놓치면 안 되는 것이라 쿼리가 담당한다.

시각은 clock_timestamp() — Postgres now()는 트랜잭션 고정이라 시간 판정이 무력화된다(Phase 1 실측).

② 최근 창 — 14일

최근 14일의 발화 전사문과 그 발화의 오류(원문 조각·교정·이유·severity·confidence). 지금 상태를 알려준다.

14일은 유도값 — 복습 최장 간격 7일의 2배로 "1·3·7일 주기를 한 번 이상 완주한 구간". 근거 문서에 14일이 직접 있는 것은 아니다 (결정 필요 ①).

③ 만성 약점

숫자 지표(계산) + Claude 관찰 노트(저장). 오래 끌고 있는 것을 알려준다.

최근 창만 보면 3개월째 못 고치는 문제를 놓친다.

이 설계가 새로 확정하는 것 — 누가 next_review_at을 쓰는가. 현재 이 컬럼에 값을 넣는 코드가 없어 ① 목록이 항상 비어 있다. 그래서 쓰기 주체를 여기서 정한다: 분석 결과 저장 트랜잭션에서 함께 갱신하고, 새 패턴은 발화 시각 + 1일, 이미 있는 패턴이 다시 발생하면 단계를 1일로 되돌린다(다시 틀린 패턴을 7일 뒤로 미루면 복습의 의미가 없다). 완주하면 1일 → 3일 → 7일로 진행하고, 3단계를 소진한 뒤 재발하면 그 사실이 만성 신호가 된다. review_tasks를 처음 사용하는 부분이다.

세션 지시문 — 수준에 맞춘 응대

agent-system-prompt.md가 고정부다 — 한 번에 질문 하나, 사용자가 65% 말하기, 교정 5단계 순서, 종료 형식. 이 설계는 그 위에 가변부를 얹는다: 오늘의 CEFR 목표, 초점 패턴과 목표 형태, 목표 문장 길이대, 힌트를 얼마나 이르게 줄지, 오늘 쓸 상황 목록.

포트 확장이 필요하다. 현재 VoiceAdapter.start()가 인자를 받지 않아 (app/audio_gateway/port.py:46) 지시문을 넘길 자리가 아예 없다. start(instruction)으로 확장한다.

이 확장은 이미 허용돼 있다 — AC 문서가 "포트가 고정하는 것은 데이터 경로이고 제어 연산은 Phase 2에서 인터페이스가 확장된다. 목표는 인터페이스 무변경이 아니라 그 확장이 Gateway 상위 로직에 파급되지 않는 것"이라고 정했다. 따라서 이 변경은 어댑터 구현체와 factory에만 닿고 세션 수명·저장·job 등록에는 닿지 않아야 하며, import 그래프 검사로 강제한다.

이것이 "내 실력에 맞춰 응대하는 Agent"의 실현 경로다. 응대하는 쪽은 Nova(빠름), 어떻게 응대할지 정하는 쪽은 Claude(미리·비동기). Claude가 실력·약점을 보고 지시문을 써서 Nova에게 건네주고, Nova가 그 지시문대로 대화한다. 지금은 agent-system-prompt.md에 "A2-B1"이 글자로 박혀 있어 실력이 올라도 바뀌지 않는다.
11 · CHRONIC WEAKNESS

만성 약점 — 숫자는 계산, 통찰은 노트

숫자 — 새로 저장할 것이 없다 (라이브 DB로 확인)

만성 신호계산 방법새 컬럼
누적 빈도error_patterns.frequency✓ 이미 있음
재발 세션 수count(distinct u.session_id)✓ 불필요
재발 일수 (서로 다른 날)count(distinct 현지날짜)✓ 불필요
지속 기간max(u.created_at) - min(u.created_at)✓ 불필요
휴면 후 재발 (최대 공백)occurrence 시각에 lag()✓ 불필요
실측으로 찾은 함정 — error_patterns.created_at을 지속 기간의 시작으로 쓰면 안 된다. 라이브 DB에서 last_seen_at - created_at이 음수(−3.8초)로 나왔다. 패턴 행의 insert 시각과 발화 시각이 서로 다른 출처이기 때문이다. 지속 기간은 반드시 발화 시각의 min/max로 계산한다. Phase 1이 last_seen_at을 발화 시각 기준으로 정한 것과 같은 이유다.

휴면 후 재발이 가장 날카로운 신호다. frequency=5가 하루에 몰린 것과 3개월에 걸쳐 흩어진 것은 완전히 다르고, 그중 한동안 사라졌다가 다시 나온 것이 가장 위험하다.

산정은 조회 시 계산으로 둔다. 롤업 테이블 안은 채택하지 않았다 — 단일 사용자 규모에서 결과가 같고 갱신 시점·신선도 관리만 늘어난다.

Claude 관찰 노트 (learner_notes)

숫자가 담을 수 없는 관찰을 보존한다. 예: "짧은 문장에서는 관사를 붙이는데 문장이 길어지면 빼먹는다", "일상 문맥에서는 맞고 업무 문맥으로 옮기면 같은 오류가 재발한다". 이런 건 재발 일수·지속 기간을 아무리 봐도 나오지 않고, 실제 문장을 읽어야 나온다.

  • 계획 생성과 같은 Claude 호출에서 갱신한다 (호출 1회로 계획 + 노트)
  • 덧붙이기만 하고 지우지 않는다. 최신 행이 현행 노트이고 과거 행이 남는다 — 노트가 이상해지면 데이터 삭제 없이 되돌릴 수 있고, 노트의 변화 자체를 관측할 수 있다
  • 노트가 읽은 발화 범위를 함께 적어 어떤 근거로 쓰인 노트인지 추적한다
12 · LEVEL ADAPTATION

수준 적응 — 실력이 오르면 난이도가 따라 오른다

PRD.md:58이 "성공률에 따라 난이도를 조절한다"를 요구하는데, current_level은 아무도 갱신하지 않아 영구히 A2다.

근거 데이터

  • pattern_attempts의 정답률 (새 테이블)
  • 발화 길이 추이 — utterances.transcript에서 계산, 소급 가능

계획 생성 Claude 호출이 "유지 / 상향 / 하향"과 그 이유를 산출하고, 워커가 같은 트랜잭션에서 갱신한다.

제약 3개

  • 한 번에 한 단계씩만 (A2 → B1 → B2). 두 단계 도약은 거부 — h-doc이 경고한 "목표 수준을 현재 수준으로 착각"을 구조로 막는다
  • 하향도 허용한다. 상향만 가능하면 잘못 올라간 수준이 굳어 매 세션이 어려워진다
  • 변경 사유를 learner_notes에 같은 append 행으로 남긴다 (별도 테이블 없음)
