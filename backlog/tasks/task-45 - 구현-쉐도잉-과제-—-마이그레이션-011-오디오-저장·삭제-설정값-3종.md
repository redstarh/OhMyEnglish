**AC#2 완료 — 설정값 3종 + `.env.example`** (설계서 §7.1~§7.3).
산출: `app/backend/app/config.py` 의 `Settings` 에 `shadowing_playback_rate`(`ge=0.5, le=2.0`, 기본 1.0) · `shadowing_repeat_count`(`ge=1, le=10`, 기본 1) · `shadowing_audio_root`(`Path("../../assets/audio")`) 추가. `from pathlib import Path` 도 함께. **새 설정 체계를 만들지 않고 같은 클래스에 더했다.**
`.env.example` 도 갱신했다 — 설계서 §7.3 이 「작업세션이 정한다」로 열려 있던 질문에 **갱신한다**로 답했고 근거는 발명이 아니라 **선례**다(`DRILL_TURNS_MIN`·`DRILL_COUNT` 가 이미 근거 주석까지 달고 그 파일에 있다).

**red→green (직접 관측)**: 신규 테스트 **8건**(파라미터화 포함) → **8 failed** → 구현 후 **8 passed**. ⚠️ red 의 형태가 둘이었다: 기본값·경계값 테스트는 `AttributeError`(필드 부재), **거부 테스트는 `Failed: DID NOT RAISE`** — `model_config` 의 `extra="ignore"` 때문에 **미지의 필드가 조용히 무시되어** 값역 위반이 통과했다. 즉 이 값역 테스트는 「필드가 존재한다」까지 함께 잠근다.

**기본값을 항등원으로 둔 것이 유일한 판단이다** (설계서 유도 3). 캡틴 결정 6은 **값역만** 정했고 기본값을 말하지 않았다 — 관측 없이 중간값(예: 3회)을 고르면 그 숫자가 코드에 굳고 나중에 「누가 3을 정했나」에 답할 사람이 없어진다.

**내가 직접 확증한 사실 1건** — 설계서 §4.3 의 근거가 참이다. 패턴을 읽는 대신 `git check-ignore -v` 로 물어봤다: `assets/audio/x.wav` → `.gitignore:32` 에 걸려 무시됨 · **`app/backend/assets/audio/x.wav` → 무시되지 않음(= 추적 대상)**. 그래서 `shadowing_audio_root` 기본값이 `../../` 인 것은 편의가 아니라 **추적 회피**이고, 백엔드 트리 안으로 옮기면 학습자 녹음이 git 에 들어간다. 테스트가 그 성질을 단정한다.

**게이트 (이 턴에 직접 돌렸다)**: **766 passed**(기준선 758 + 신규 8 · 회귀 0) · `ruff check .` exit 0 · `ruff format --check .` 33 files · `ty check` exit 0 · 게이트 밖 `ruff` **6 errors** · `format --check ../../tests` **4 files**(기준선 유지).

⛔ **AC#1·#3·#4·#5·#8 은 착수하지 않았다 — 설계서 자신의 게이트가 막는다. 이것을 「안 한 것」이 아니라 「막힌 것」으로 읽어라.**

설계서 §9 의 **⛔「마이그레이션 파일을 쓰는 조건 — 지금은 쓰지 않는다」**가 `011_shadowing_items.sql` 을 **선행 2개 뒤로** 미룬다. 근거는 `data-first` §3 의 「소비자가 0곳이면 진행하지 않는다」이고, 설계서가 **이 리포는 같은 실패를 네 번 냈다**(값을 저장하는데 읽는 코드가 0곳)고 적었다. **선행 둘을 직접 확인했고 둘 다 미충족이다**:
1. **`TASK-10` 이 쉐도잉 진입점을 확정했다** → `TASK-10` 은 **`To Do`** 이고 그 자신이 `TASK-2` 를 기다린다(`backlog task view TASK-10` 실행 결과).
2. **`create_session` 이 `mode` 를 받는다** → 실측 시그니처가 **`create_session(pool: asyncpg.Pool, user_id: UUID)`** 다(`app/backend/app/services/sessions.py`). `_CREATE_SESSION_SQL` 이 `mode` 를 **하드코딩**한다.
→ 그래서 **`--dep TASK-10` 을 걸었다**(기존 `TASK-27` 과 함께). 파이프라인이 눈에 보이게 멈추는 것이 옳다.

**추가 실측 — 011 은 독립된 두 묶음이고 게이트가 걸리는 곳이 다르다:**
- **묶음 A** (§3.3): `shadowing_items` 표 + `learning_sessions.shadowing_item_id` + `check (shadowing_item_id is null or mode = 'shadowing')`. **소비자가 `TASK-10` 이라 게이트에 정면으로 걸린다.** ⚠️ `learning_sessions.mode` 값역에는 **이미 `'shadowing'` 이 있다**(001 실측) — 막는 것은 값역이 아니라 **`mode` 를 받는 진입점이 없다는 것**이다.
- **묶음 B** (§4.2): `utterance_type` 값역에 `shadowing_recording` 추가 + `audio_url` 을 그 값에만 허용하는 CHECK + 부분 인덱스. 소비자(서빙 엔드포인트·삭제 스윕)는 **이 태스크가 소유**한다(AC#3~#5). ⚠️ 그런데 **생산자**가 묶음 A 를 거쳐야 하므로 실물 데이터는 여전히 흐르지 않는다. 그리고 설계서 약점 1 이 이것을 **「되돌릴 수 없는 방향으로 굳는다」**로 지목한다(114행 든 표의 CHECK DROP→ADD · `shadowing_recording` 행이 하나라도 생기면 되돌리기 스크립트가 실패한다).
- 실측: `utterances.audio_url` **컬럼은 이미 있다**(nullable · 채워진 행 **0**) · `utterance_type` 값역은 `('learning','voice_command','command_confirmation')` · `utterances` 총 **114행**.

**⚠️ 캡틴에게 올릴 것 — 결정 25 를 문자대로 이행하면 그 목적이 달성되지 않는다.**
결정 25 는 *"너가 추정 클립을 수집해서 **간단한 학습이 가능하도록** 일단 시작해"* 다. 그런데 표를 만들고 시드를 채워도 **진입점(`TASK-10`)과 `create_session(mode)` 가 없으면 학습이 성립하지 않는다** — 아무도 그 클립을 고르지 않는다. 즉 011 을 지금 쓰는 것은 **게이트를 어기면서 결정 25 의 목적도 달성하지 못하는** 선택이다.
→ 물을 것: **`TASK-45` 를 여기서 멈추고 `TASK-10`·`TASK-2` 를 먼저 열까**, 아니면 **`create_session(mode)` 배선 + 최소 진입점을 이 태스크 범위로 넓혀 011 까지 한 번에 갈까.** 후자는 `TASK-10` 의 설계 몫을 구현이 선점하는 것이라 팀리드 단독으로 정하지 않는다.
⛔ **그 답이 오기 전에 011 을 쓰지 않는다.** 되돌릴 수 없는 CHECK 변경이 그 안에 있다.

**캡틴 결정 34 (2026-09-08) — 게이트가 풀렸다. `TASK-45` 가 최소 진입점까지 소유한다.**
위 「캡틴에게 올릴 것」의 두 갈래 중 **「지금 돌아가게 만들자 (입구까지)」**를 캡틴이 골랐다. → 설계서 §9 의 ⛔ 게이트가 요구한 선행 둘(진입점 · `create_session(mode)`)이 **이 태스크 범위**가 됐으므로 **011 을 쓸 수 있다.** `--dep TASK-10` 을 **뗐다**(그것이 선행이 아니게 됐다).
⚠️ **대가와 제약은 결정 34 본문이 소유한다** — 요지: 최소한만 만든다(추가 학습 5종 배치는 `TASK-10` 이 그대로 소유) · 되돌리기 쉬운 형태로 짜고 **무엇을 선점했는지 적는다** · 011 의 되돌릴 수 없는 부분은 010 의 적용 5단계를 그대로 쓴다.
